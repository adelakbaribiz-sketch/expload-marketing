# USE-CASES.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Detailed flows for the platform's most complex or highest-risk features, recovered directly from route/handler code — not idealized descriptions. Exception flows include real gaps found in code, not just happy-path assumptions.

## UC-1: Tenant Signup with Auto-Setup

**Actor**: Anonymous visitor
**Preconditions**: None — publicly reachable.
**Main flow**:
1. Visitor submits name, email, password (≥8 chars), tenant name, tenant domain to `POST /api/auth/signup`.
2. System validates via zod, sanitizes text fields, hashes the password (bcrypt, cost 12).
3. System creates a `Tenant` and the first `User` with `role: 'owner'` in one transaction.
4. System runs an "auto 1-click setup": seeds a default project, 5 demo leads, a welcome email template, 4 fraud rules, a marketing funnel (`Default Funnel`, event-keyed stages, no volume data), a customer journey (`Welcome Journey`, signup-triggered), Bronze club-tier enrollment with 100 signup points, 3 default rewards, a progressive-unlock roadmap entry, and 2 default goals.
5. Client auto-logs in with the just-created credentials and redirects into the dashboard.
**Alternate/exception flows**:
- A.1 — Auto-setup step fails partway (e.g. DB error mid-seed): the response includes an `autoSetup` array of which steps succeeded; the client shows a partial-success message rather than failing signup outright. Tenant creation itself is not rolled back if a later seed step fails.
- A.2 — Domain already taken: 400, signup rejected.
**Postconditions**: A fully isolated tenant exists with sample data across ~8 domains, ready to explore without an empty-state dead end.
**Business rules applied**: none of the negotiation/payroll/tier formulas — this is a pure provisioning flow. See `BUSINESS-RULES.md` §6 for the Bronze-tier signup bonus.

## UC-2: Team Invite & New-User Acceptance

**Actor**: Tenant owner/admin (inviter), a new or existing person (invitee)
**Preconditions**: Inviter is authenticated in a tenant.
**Main flow**:
1. Inviter submits invitee email, name, and role via the Team view.
2. System creates a `TeamInvitation` (7-day expiry, random token), logs an audit entry, and returns a shareable link (`/invite/{token}`).
3. Inviter copies and sends the link out-of-band (email/chat — the system does not send it itself).
4. Invitee opens the public `/invite/{token}` page, which fetches invitation status.
5a. **If the invitee's email has no existing account**: the page shows a name+password form; on submit, the system creates a real `User` (hashed password) in the inviter's tenant with the invited role, marks the invitation accepted, and logs the new user in immediately.
5b. **If the invitee's email already has an account**: the page shows a one-click "Accept" (no password needed) that reassigns that existing user's `tenantId`/`role` to the inviting tenant and marks the invitation accepted.
**Alternate/exception flows**:
- A.1 — Token expired or already accepted/rejected: page shows an error state, no action possible.
- A.2 — Existing-account acceptance path does not verify the accepting session belongs to the actual owner of that email — it trusts that possessing the token (sent out-of-band) is sufficient proof, matching the token's role as the actual secret.
**Postconditions**: Invitee has an active account in the inviter's tenant with the assigned role.
**Note**: this flow was non-functional before this session's Phase 1 fix (invite links pointed at an API path with no page behind them, and the accept endpoint silently did nothing for genuinely new emails).

## UC-3: Lead Discovery & AI Enrichment

**Actor**: Tenant team member
**Preconditions**: Authenticated, has `leads.create` permission (nominally — see `BUSINESS-RULES.md` §2 on RBAC enforcement gaps).
**Main flow**:
1. User searches by industry/location.
2. System calls Serper.dev (Google search) and/or the Google Maps scraper (3-tier: Playwright DOM scrape → Serper Places API → deterministic mock) to find matching businesses.
3. Results are enriched with AI-extracted structured data (industry, services, contact info) via the LLM aggregator or `z-ai-web-dev-sdk` depending on the call site.
4. Each lead is scored and persisted, tagged with its `source` (`real` vs `mock`).
**Alternate/exception flows**:
- A.1 — No `SERPER_API_KEY` configured: falls back to a seeded deterministic mock result set, explicitly labeled `source: 'mock'` in the response so the caller can tell.
- A.2 — Playwright unavailable/disabled: skips tier 1, tries Serper Places, then mock.
**Postconditions**: New `Lead` records exist, scored and enriched, visible in CRM.
**Business rules applied**: none beyond the graceful-degradation pattern noted as a hidden NFR in `PRD.md` §5.

## UC-4: AI Negotiation — Full 6-Round Cycle

**Actor**: A prospective customer (via the public project-intake/onboarding flow) and the platform's AI
**Preconditions**: An onboarding session with business context (crawled website + uploaded docs + generated system prompt) exists.
**Main flow**:
1. System generates Round 0 (Initial) proposal via the LLM, using onboarding context.
2. Customer reviews and either accepts (→ `accepted`, flow ends) or rejects.
3. On reject, system auto-generates the next round's proposal per the formula in `BUSINESS-RULES.md` §3 (MVP → Economic → Phased → Revenue-Share → Equity).
4. Every state transition and proposal is logged to `NegotiationAuditEvent`.
5. If Round 5 (Equity, final) is rejected, state becomes `rejected_all` — no further automatic proposals.
**Alternate/exception flows**:
- A.1 — LLM returns malformed JSON: a parsing fallback handles it, but the exact behavior (retry vs. rule-based substitute) was not independently re-verified this pass beyond confirming a fallback path exists.
- A.2 — Customer can request a manual "regenerate" of the current round's proposal without rejecting (a distinct action from reject-and-advance).
**Postconditions**: Either an accepted deal at some round's terms, or a fully-rejected negotiation with a complete audit trail.
**Important caveat**: the discount percentages are *targets given to the LLM*, not hard constraints validated against its output — see `BUSINESS-RULES.md` §3.

## UC-5: Distributor License Purchase & Allocation

**Actor**: A `Tenant` with `plan: 'distributor'`, linked `Distributor` record
**Preconditions**: Distributor account exists with a tier (standard/silver/gold/platinum/master); superadmin has published `LicensePackage` SKUs.
**Main flow**:
1. Distributor selects a `LicensePackage` (e.g. PLT-500) to purchase.
2. System checks `pkg.tierRestriction` against the distributor's tier — rejects (403) on mismatch.
3. System generates `count` unique license keys, sets each to expire `pkg.validityMonths` from now, status `in_pool`.
4. System increments `distributor.totalLicensesPurchased` by `count` and `totalPaidToPlatform` by `pkg.wholesalePrice` **(flat, not multiplied by count — see the flagged calculation issue in `BUSINESS-RULES.md` §5)**.
5. Distributor later allocates individual keys from the pool to their own end customers (status transitions `in_pool → allocated → activated`, or `→ expired`/`→ revoked`).
**Alternate/exception flows**:
- A.1 — Distributor requests a payout of accumulated sales: creates a `DistributorPayout` with `grossSales`/`platformShare`/`distributorShare` **supplied directly by the caller, with no formula computing what those amounts should actually be** — a real, unresolved gap (`BUSINESS-RULES.md` §5). Approval/payment status still goes through a real superadmin-gated workflow (`pending → approved → paid`).
**Postconditions**: License pool updated; (if payout requested) a payout record in the approval queue.

## UC-6: Payroll Run

**Actor**: SuperAdmin or an authorized internal employee
**Preconditions**: `PayrollConfig` exists (or defaults apply: 50/40/10/5 split, role weights per `BUSINESS-RULES.md` §4); a period's revenue figure is available; employees have approved timesheets where applicable.
**Main flow**:
1. Operator triggers `POST /api/payroll/run` for a period with a `totalRevenue` figure.
2. System computes `ownerShare`, `staffPool`, `reinvestment`, `bonusPool` per the fixed percentages.
3. For each active internal employee, system computes hours (real approved timesheet hours if VA-linked, else a flat 160h assumption), applies their role weight, and derives a proportional share of the distributable pool plus an equally-proportional "bonus" share.
4. System applies a flat 10% tax withholding to each employee's gross share.
5. Period moves `draft → calculated`; a human then reviews and moves it `→ approved → paid`.
**Alternate/exception flows**:
- A.1 — A salaried, non-VA-linked employee's actual hours worked differ from 160 for the period: payroll is inaccurate for them, silently — the system has no way to know, since it never asked.
- A.2 — `performanceFactor` in the formula is always 1.0 regardless of actual performance data that exists elsewhere in the schema (`AssistantPerformance`) — no employee's pay is currently affected by performance.
**Postconditions**: `SalaryPayment` records exist per employee for the period, summing to (approximately) the staff pool.

## UC-7: Support Ticket Lifecycle with SLA

**Actor**: A tenant with an active `SupportSubscription`; a support agent (internal employee)
**Preconditions**: Tenant has subscribed to a `SupportPlan`.
**Main flow**:
1. Tenant submits a ticket (subject, description, category, priority).
2. System looks up the tenant's active subscription's plan and stamps `slaResponseDue`/`slaResolutionDue` on the ticket at creation, based on that plan's response/resolution hours (falls back to 48h response if no active subscription is found).
3. An agent responds; `firstRespondedAt` is set on the first agent message.
4. Ticket proceeds through status/priority changes until resolved; customer may rate the experience.
**Alternate/exception flows**:
- A.1 — SLA deadline passes with no response: **nothing happens.** No flag is set, no notification fires, no escalation occurs. The deadline field exists purely as data — this use case's "guarantee" is not operationally real today, only contractually implied by the pricing page.
**Postconditions**: Ticket resolved or ongoing; SLA compliance is not measurable from within the system as currently built (would require an external report comparing `slaResponseDue` to `firstRespondedAt` manually).

## UC-8: Sandbox Demo → Real Signup Conversion

**Actor**: Anonymous visitor
**Preconditions**: None.
**Main flow**:
1. Visitor starts a sandbox session (`POST /api/sandbox/start`) with just an email — no password, no real tenant. System creates a `SandboxSession` (24h expiry, 20-action cap) backed by a mock tenant.
2. Visitor performs demo actions (`POST /api/sandbox/action`), each logged and counted against the cap.
3. Visitor converts (`POST /api/sandbox/convert`) at any point to create a real account.
**Alternate/exception flows**:
- A.1 — Session expires (24h) or action cap (20) is reached: further actions presumably rejected (not independently re-verified this pass whether the response includes a clear "upgrade to continue" prompt).
- A.2 — This entire flow, including `start`/`action`/`convert`, is in `proxy.ts`'s public allowlist with **no rate limiting applied** — see `KNOWN-ISSUES.md` #12, a resource-exhaustion exposure distinct from the intended demo-limiting logic (the cap limits *one session's* actions, not how many sessions an attacker can create).
**Postconditions**: Either an expired/abandoned demo session, or a newly-created real tenant.

## UC-9: Approval Workflow Submission (built this session)

**Actor**: A tenant team member (requester), a manager/owner (reviewer)
**Preconditions**: Authenticated in a tenant.
**Main flow**:
1. Requester manually opens "New Request," selects a type (campaign/content/social_post/ad/workflow/budget), enters an item id and description, optionally a comment.
2. Request is created with status `pending`.
3. Reviewer sees it in the Pending filter, clicks Approve or Reject; system stamps `reviewedBy`/`reviewedAt` and updates status.
**Alternate/exception flows**:
- A.1 — No other feature in the codebase automatically creates an `ApprovalRequest` — this is currently a manually-invoked tool, not an enforced gate in front of publishing a campaign/ad/content piece. A requirement that "campaigns must be approved before sending" would need new integration work at each publish point, not just this queue.
**Postconditions**: Request in a terminal state (approved/rejected), fully attributed and timestamped.
