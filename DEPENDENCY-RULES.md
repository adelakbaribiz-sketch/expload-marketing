# DEPENDENCY-RULES.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04, Phase 3. The enforceable version of `MODULE-BOUNDARIES.md` — concrete rules for what may import what, going forward. Baseline is genuinely good (verified: zero circular dependencies, clean service/HTTP separation almost everywhere) — these rules exist to *keep* it that way as the codebase grows, and to close the specific gaps found.

## Rule 1 — Layer direction is one-way: UI → HTTP → Service → Data

- `src/components/**` may import from `src/lib/**` **only** for pure, client-safe, static-data or formatting utilities (confirmed today: `utils.ts`'s `cn()`, `guides/section-guides.ts`). Anything that touches `db`, `next/headers`, `node:crypto`, or any file marked `'server-only'` is forbidden from a component import, no exceptions.
- `src/app/api/**/route.ts` files must never import another `route.ts` file. (Currently true — zero violations found. Keep it that way: if two routes need to share logic, extract it to `src/lib/`, don't import between routes.)
- `src/lib/**` (except `src/lib/crud/domain-handler.ts` and `src/lib/security/{headers,rate-limit,with-protection}.ts`, which exist specifically to produce/wrap route handlers) must never import `next/server`, `NextRequest`, or `NextResponse`. A service module should be callable from a script, a test, or a different route with no HTTP context.
- `src/proxy.ts` is the **only** sanctioned exception to "HTTP layer should reuse the service layer" — it inlines its own HMAC logic because the Edge runtime can't reliably import `src/lib/auth`. Do not use this as precedent for any other shortcut.

## Rule 2 — No new circular dependencies

The current `src/lib/` dependency graph is a clean DAG (verified, zero cycles, traced 3-5 hops deep). Before adding an import between two `src/lib/` modules, check it doesn't create a cycle — most straightforwardly, service modules that emit events (`negotiation`, `llm`, `graph`, `finance`, `campaign-scheduler`, `project-intake`) should only ever import `notifications/emitter.ts`, never the other direction (the emitter must never import a domain service).

## Rule 3 — Every domain that has a real business rule needs a `src/lib/` module; the CRUD factory is for pure CRUD only

If a domain built on `createDomainHandlers`/`createDomainItemHandlers` ever needs validation beyond field-name allowlisting, a computed field, a side effect, or a calculation — **do not** special-case the factory. Either give that domain a small dedicated `src/lib/<domain>/` module and switch it to a bespoke route that calls into it (matching the negotiation/payroll/LLM pattern), or extend the factory's `DomainConfig` with an optional `validate?: (body) => ...` / `beforeCreate?: (data) => ...` hook that stays generic (accepts a function, doesn't know what's inside it). Never add `if (config.model === 'X')` branches inside `domain-handler.ts` itself — that would turn a clean, reused-by-46-domains abstraction into exactly the kind of tightly-coupled god module this audit confirmed doesn't currently exist.

## Rule 4 — One AI integration boundary, not two

Any new AI-powered feature must go through `src/lib/llm/aggregator.ts`. Do not add a new direct `z-ai-web-dev-sdk` call site — the 5 that exist today are a known, tracked liability (`KNOWN-ISSUES.md` #14), not a pattern to extend. See ADR-0002 for the consolidation plan.

## Rule 5 — Prefer direct module composition over internal HTTP self-calls

`src/lib/graph/orchestrator.ts`'s pattern of calling its own API routes via `fetch()` for each of ~15 node types should not be extended to new node types, and should be migrated away from where practical (see ADR-0005). A `src/lib/` module calling another `src/lib/` module directly is faster, type-checked at compile time, and doesn't silently break when a route's request/response shape changes. Reserve internal HTTP self-calls for cases that genuinely need HTTP semantics (e.g. triggering a webhook-style callback), not routine cross-domain composition.

## Rule 6 — The tenant-context resolver is a security boundary, treat it like one

`getTenantId()`/`requireTenantId()` (`src/lib/tenant.ts`) must never be extended with a new "convenience" fallback source without an accompanying credential check. See ADR-0004 for the required fix to the two fallback sources that exist today.

## Rule 7 — One source of truth per cross-cutting concern

Confirmed duplications to resolve, not extend: two "autonomous agent" implementations (`graph/orchestrator.ts` vs. `api/agent/run/route.ts` — ADR-0005); a prompt catalog (`prompts/system-prompts.ts`) that most AI-calling modules bypass in favor of inline duplicate prompts — new AI features should register their prompt in the catalog and import it, not inline a new one; two onboarding step-tracking systems (`OnboardingStep` vs. `OnboardingSession`, per `BUSINESS-RULES.md` §9) with no sequencing enforcement in either — consolidate to one before adding to either.

## Rule 8 — Dead code found in this audit should be removed, not built around

`src/lib/payment/gateway-router.ts` and `src/lib/onboarding/extractor.ts` are complete, working-looking modules that nothing calls. Do not add a third onboarding-document-parsing path or a second payment-gateway router alongside these — either wire the existing ones in (they appear otherwise finished) or remove them; adding a parallel implementation because "the existing one seems unused" would create exactly the kind of duplication Rule 7 exists to prevent.
