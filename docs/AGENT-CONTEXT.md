## What this project is

**Expload Marketing** — a multi-tenant B2B marketing SaaS (Next.js 16, Prisma, TypeScript) that is simultaneously a full marketing-automation platform for its direct customers *and* a wholesale/white-label reseller business (distributors buy license packages and resell the platform) *and* an internal-operations tool (payroll, HR, support SLAs) for whoever runs it. Full detail: `docs/PRODUCT-BASELINE.md`.

## What's actually built (verified, not assumed)

76 API domains / 239 routes. 150 Prisma models. 62 dashboard views, all correctly wired (zero orphans, verified by tracing every `page.tsx` switch case against every nav entry and component file). Real, working: CRM, lead gen (with honest mock-fallback), email campaigns, a real multi-provider LLM aggregator, an AI negotiation engine (6-round automatic concession formula, exact numbers in `BUSINESS-RULES.md` §3), an LLM-driven graph/DAG orchestrator, crypto payments, a wholesale license/distributor system, Redis-backed job queue with in-memory fallback, Qdrant vector search with in-DB fallback, 29-language i18n with RTL. Full status per module: `REQUIREMENTS-TRACEABILITY.md`.

## What's broken or fake (do not assume these work just because the UI/schema exist)

- 11 of 15 "configured" payment gateways make zero real API calls (Stripe's `clientSecret` literally contains the string `_mock`) — only NOWPayments crypto is real.
- 4 "analyzer" features (backlink discovery, competitor analysis, social analyzer, SEO crawl) unconditionally return `Math.random()`-fabricated data, persisted as if real.
- WhatsApp and SMS have full CRUD + UI, zero actual send integration.
- Onboarding document upload (`src/lib/onboarding/extractor.ts`) has zero callers — never actually parses anything despite looking finished and having `mammoth`/`pdf-parse` installed.
- Two disconnected AI stacks: `llm/aggregator.ts` (real, portable) vs. `z-ai-web-dev-sdk` (5 call sites, environment-coupled, likely won't work in a fresh self-hosted deployment).
- Two independent, non-communicating "autonomous agent" implementations (`graph/orchestrator.ts` vs. `api/agent/run`).
- Custom role/permission editor in the UI still has **no real effect for custom roles specifically** — the `Permission` table is never seeded, so a custom `Role`'s granted permissions never match anything real. (Update 2026-09-05: `hasPermission()` itself is now actually wired into several routes — `team/members`, `team/invite`, `team/roles`, payroll — but those checks only ever resolve `true` for `owner`/`SuperAdmin`/platform-staff-admin, i.e. the same conservative default as before; the custom-role granularity this UI implies still does nothing until real `Permission` rows exist.)
- No CI/CD. No APM/observability tooling. Automated tests: a first, narrow `bun test` suite (23 tests) was added in Phase 08, scoped to what that phase touched (the pricing engine, the CRUD factory's query helpers, and the club-rewards-redeem concurrency fix); Phase 09 added the project's first E2E suite (Playwright, `e2e/critical-journeys.spec.ts`, `bun run test:e2e` against `bun run e2e:build` — must run against a production build, not `next dev`, see the Phase 09 note below) — this is still not a QA program; the other ~235 route files and most user flows have zero test coverage.
- **Until 2026-09-06, every authenticated write request would have failed in the actual deployed (standalone/Docker) environment** — `proxy.ts`'s CSRF check compared the browser's Origin against the server's own bind address instead of the `Host` header. Fixed; see the Phase 09 note below. If you ever see `cross_origin_request_denied` again, this is the first place to check, and always test against a real production build (`bun run e2e:build`) at least once when touching `proxy.ts` — `next dev` cannot catch this class of bug.

**Update 2026-09-05 (Phase 05, security)**: `THREAT-MODEL.md`/`SECURITY-BASELINE.md`/`SECURITY.md` — a full 26-area audit found and fixed 14 Critical + 9 High findings, live-verified against a running server (`scripts/security-checks.ts`, `bun run security-check`). The single most important one to know about if you're touching auth/team code: `POST /api/team/members`, `PATCH /api/team/members/[id]`, `POST /api/team/invite`, `PATCH /api/team/roles/[id]` now all require `hasPermission('team.manage')` (owner/SuperAdmin only in practice — see the RBAC note above), and `POST /api/team/invite/[token]` accepting an invite for an **existing** account now requires that account's real password. Any new team-management route must follow the same pattern — do not add a bare `requireTenantId()`-only check to anything that changes a user's role or moves them between tenants. Also new: `src/lib/security/ssrf-guard.ts` — reuse `assertPublicHost()` for any future feature that has the server fetch a user-supplied URL, don't re-derive the private-IP check. Payment-gateway secrets (`GET /api/payments/gateways`) now require `isSuperAdmin()` and never include `apiKey`/`secretKey`/`webhookSecret` in the response — if you add a new field to `PaymentGatewayConfig`, default to NOT returning it from GET unless there's a specific reason the frontend needs to read it back.

**Update 2026-09-04 (Phase 08, backend)**: `BACKEND-ARCHITECTURE.md` — full audit of all 239 routes across Validation/Business Logic/Authorization/Transactions/Error Handling/Logging/Caching/Background Jobs/Events/API Versioning/Pagination/Filtering/Sorting. The two things every future route must know: (1) `withProtection()` (`src/lib/security/with-protection.ts`) now catches any uncaught exception and returns a clean `{ error }` JSON response — throw `ApiError(status, message)` (`src/lib/api/errors.ts`) from inside a handler, including from inside a `db.$transaction` callback, to control the exact status/message instead of falling through to a generic 500; (2) the CRUD factory (`src/lib/crud/domain-handler.ts`) now supports `?page=`/`?limit=` pagination, optional `filterableFields`/`sortableFields` on `DomainConfig`, and the `validate`/`beforeWrite` hooks from `adr/0003` (now Implemented, not just Proposed) — and its GET handlers are now wrapped in `withProtection` (they previously had **no** protection at all: no rate limit, no error handling, across all 91 factory-backed domains). All 8 of DB-08's missing transactions shipped, including atomic-guard fixes for 2 real TOCTOU races (club rewards redeem, club ad-credit spend) — see `src/lib/club/redeem-reward.ts` for a worked example of extracting business logic out of a controller into something independently testable. `src/lib/billing/pricing-engine.ts` is now the single source of truth for plan-recommendation/ROI scoring — do not re-implement that algorithm in a new route, import from there.

**Update 2026-09-06 (Phase 09, frontend)**: `FRONTEND-ARCHITECTURE.md` — full audit of the client app. The critical thing every future contributor must know: **`proxy.ts`'s CSRF Origin check was broken against a real production build** (compared against `req.nextUrl.origin`, the server's own `0.0.0.0` bind address, not the browser's actual host) — every authenticated write would 403 once deployed. Now fixed to use the `Host`/`X-Forwarded-Proto` headers. This was undetectable via `next dev` and only surfaced by running the project's first E2E test against `.next/standalone/server.js` — **always verify against a production build, not just dev, when touching `proxy.ts` or anything auth/session-related.** Also fixed: `club/membership`'s `earn_points` action had no permission check and no input bounds (any tenant user could mint arbitrary points server-side, with no UI even referencing the action) — now requires `isPlatformStaffAdmin()` and bounded inputs; `leads`/`campaigns` write routes now call a new `requireNonViewer()` (`src/lib/auth/rbac.ts`) instead of relying on the frontend's `canWrite` check alone; `team/members` can no longer be used to grant `role: 'owner'` except by an existing owner/SuperAdmin. The frontend itself: `page.tsx`'s 63 dashboard views are now `next/dynamic`-code-split (were 100% statically imported — check `ViewLoading`'s pattern before adding a 64th view the old way); `src/lib/api-client.ts` is the new shared fetch wrapper (adopted so far only in `crm-view.tsx` — prefer it over a raw `fetch()` in new code); `src/lib/a11y.ts`'s `onActivateKey()` is the pattern for any future non-native clickable element. The app is still a single client-rendered SPA with no per-view routing (deliberate, `adr/0001` — don't add `next/dynamic` route-level pages without a dedicated architecture decision first).

## Architecture (verified, not designed-on-paper)

Single Next.js deployable, modular monolith (deliberately — see `adr/0001`, do not propose microservices without a real evidenced need). `src/lib/**` module graph is a clean DAG, **zero circular dependencies** (traced 3-5 hops deep). Layer separation (UI → HTTP → Service → Data) is real and consistently upheld almost everywhere — full model in `MODULE-BOUNDARIES.md`. The generic CRUD factory (`src/lib/crud/domain-handler.ts`) powers 91 of 239 routes and is genuinely, confirmedly generic — never special-case it for one model; extend it via `DomainConfig`'s `validate`/`beforeWrite`/`filterableFields`/`sortableFields` (`adr/0003`, implemented Phase 08) instead. Business logic that has no service module to live in (payroll, distributors, marketplace, white-label, progressive-unlock, the autonomous agent) is a known, ranked, partially-addressed gap — see `BACKEND-ARCHITECTURE.md` §2 before adding more inline logic to one of those domains' routes.

## Database

150 Prisma models, SQLite (dev) / PostgreSQL (prod, documented). **No migration history exists — `prisma/migrations/` is empty/absent.** Never run a destructive schema operation against anything resembling production data without following the DB-safety procedure in `ARCHITECTURE-TARGET.md` (Backup → Migration → Validation → Rollback, every step explicit and written down before you start, per `adr/0006`).

## API

Two coexisting patterns: the generic CRUD factory (list/create via `requireTenantId()`, update/delete via a fetch-then-compare ownership check) and bespoke handlers (auth via `isSuperAdmin()`/`getCurrentUser()`/`requireTenantId()` depending on domain). **The tenant-context resolver `getTenantId()` (`src/lib/tenant.ts`) currently has an unauthenticated header/cookie fallback that is the root cause of this project's most severe security findings — do not add a new route that relies on `requireTenantId()` alone for anything sensitive until `adr/0004` is resolved, and do not extend the fallback pattern anywhere else.**

## What must not change without a documented reason (per this migration's own governing rules)

- Do not rewrite the CRUD factory, the negotiation engine, the LLM aggregator, or any other module confirmed clean/working in this audit trail — extend, don't replace.
- Do not delete a feature because its backing integration is a stub (payment gateways, WhatsApp/SMS) — fix the integration or get an explicit product decision to remove the feature; don't silently drop UI/schema that customers may already be relying on the *appearance* of.
- Do not "clean up" `src/lib/payment/gateway-router.ts` or `src/lib/onboarding/extractor.ts` by deleting them without checking `ARCHITECTURE-TARGET.md` item 9 first — they may be intended to be wired in, not removed.
- Do not reset the database, force-push over the git history, or run `prisma db push --accept-data-loss` against anything that isn't a throwaway dev database.
- Do not treat any prior `worklog.md` "Stage Summary: ... TypeScript clean, ESLint clean, build successful" claim as proof a feature actually works end-to-end — those checks confirm the code compiles, not that the business logic is correct or the integration is real. This audit trail exists specifically because several such claims turned out to describe stub/fake behavior underneath a clean build.
