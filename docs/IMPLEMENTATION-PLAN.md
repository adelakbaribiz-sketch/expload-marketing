# IMPLEMENTATION-PLAN.md

Generated 2026-09-04. Research phase: prior 3 audit phases (`PROJECT-INVENTORY.md` through `adr/0007`) plus a targeted supplementary check this pass — OWASP's Multi-Tenant Security Cheat Sheet and current multi-tenant SaaS practice confirm the standard fix for tenant-context spoofing is exactly `adr/0004`'s Option A/B ("derive tenant from the authenticated session/token, never trust a client-supplied header unless it's cryptographically bound") — this validates the prior recommendation rather than changing it.

**Dependency check performed before finalizing this plan** (per the project-protection rule — usage found before any removal/restriction decision):
- `getTenantId()`'s `X-Tenant-ID` header fallback: **zero legitimate callers found anywhere in `src/`** (only two files reference the header at all, both as the code that *reads* it: `tenant.ts` and `with-protection.ts`'s audit-only `getTenantIdFromRequest`). Safe to remove outright.
- `getTenantId()`'s `tenant-id` **cookie** fallback: **actively wired to a real feature** — `src/components/providers.tsx`'s `TenantSync` writes this cookie whenever the sidebar's tenant-switcher (`sidebar.tsx`, fed by `GET /api/tenants`) selects a different tenant. This is very likely how a superadmin was intended to view/manage another tenant's data from inside the dashboard. **Plan revised from the original ADR-0004 "just remove it" framing**: keep the cookie override, but only honor it when the requesting session is a real SuperAdmin — closing the vulnerability for every other user while preserving the one real feature that depends on it, per the "don't remove what's actually in use" rule.
- `GET /api/tenants`: 5 real frontend callers (`page.tsx`, `header.tsx`, `sidebar.tsx`, `tenants-view.tsx` ×2) — none require seeing *other* tenants except the superadmin switcher case above. Fix: non-superadmins get only their own tenant; superadmins keep the full list (preserving the switcher).
- `POST /api/seed`: exactly one caller, `page.tsx`'s auto-bootstrap effect, which already only fires `if (!user) return` first — i.e., only when authenticated. Gating the route behind authentication does not break this caller. The response's `credentials` field has zero readers (the caller only reads `data.tenantId`) — safe to remove from the response.
- `PATCH`/`DELETE /api/marketplace/products/[id]`: **zero frontend callers found anywhere** — safe to restrict without breaking any UI.
- `support-plans/{tickets,subscriptions}` PATCH, `leads/[id]/enrich`, `campaigns/[id]/send`: all called by their respective views with the caller's own resource ids in normal operation — adding an ownership check changes nothing for legitimate use, only rejects cross-tenant ids.

## What this pass implements

**P0 (#1-3) and P1 (#4-9) are implemented in this pass** — all are contained, dependency-checked, low-to-medium risk, and directly close the audit's highest-severity findings. Items 10-11 (P2) are **not** implemented this pass — they're foundational but don't close a live vulnerability, and this pass's time/risk budget is better spent on verifying the P0/P1 security fixes thoroughly (test-before/test-after, live browser verification) than starting new foundational work without room to verify it properly. Items 12-13 (P3) and the two BLOCKED items are explicitly deferred with reasons, not silently dropped — see `docs/PROJECT-CONTROL.md`'s "Pending decisions" for what would unblock each.
