**This file is the live control document for this project. Update it whenever a phase status, decision, or risk changes — don't let it go stale.** Last updated: 2026-09-06, after Phase 16 (Performance Engineering).

**Update 2026-09-06 (Phase 16 — Performance Engineering)**: full measurement-first performance audit (`PERFORMANCE-AUDIT.md`) — every finding below came from real timings against a running dev server with realistic seeded data (305 leads, 15 campaigns), not guesswork. **Headline finding**: `POST /api/leads/search` (AI lead enrichment) measured **21.2 seconds for 10 leads** — traced (not assumed) to `llmAggregator.complete()` doing 15 sequential DB round trips per lead (quota-check + audit-write × 5 fallback providers) before giving up, on top of the enrichment loop itself being a sequential `for` loop. Fixed both: `src/lib/llm/aggregator.ts` now fails fast on a provider with no API key configured at all, skipping the DB work entirely; `src/app/api/leads/search/route.ts` now runs enrichment with bounded concurrency (new dependency-free `src/lib/async/concurrency.ts`). Measured result: 21.2s → 6.1-6.3s (reproduced after a clean restart). Also measured: `GET /api/dashboard/unified` issues 37 parallel queries per request (~97-184ms) — added a 30s per-tenant TTL cache (new `src/lib/cache/ttl-cache.ts`, `globalThis`-cached for the same cross-route-bundle-singleton reason Phase 15's metrics registry needed it) since dashboard KPIs tolerate staleness; measured result: 97-184ms → 20-39ms steady state. Also fixed: `EmailCampaign` was the one model in the whole schema with zero `@@index` entries despite every real query filtering by tenantId — added `@@index([tenantId, createdAt])` matching the established pattern (via `prisma db push`, no measured effect yet at today's small seeded volume — framed honestly as a consistency/scale fix, not a measured speedup). **Found, not fixed (no live measurement was possible)**: none of the 5 LLM provider files put a timeout on their completion-endpoint `fetch()` calls — a real latent risk, flagged with the exact fix identified (reuse the existing `withTimeout()` from Phase 13's integrations layer) but not applied since this environment's provider keys are all empty and no real network call was ever exercised to verify against. Explicitly NOT changed, with reasoning: connection pooling (moot until Postgres is activated), queue concurrency (Redis unreachable in this dev environment, so unmeasurable; real usage doesn't obviously warrant it yet), the in-memory rate limiter (no second app instance exists yet to make it a real problem) — each a case of the phase's own "no optimization without measurement" rule being followed, not skipped.

**Update 2026-09-06 (Phase 15 — Logging, Monitoring & Observability)**: built real observability from a standing start (`OBSERVABILITY.md`) — structured JSON logging (`src/lib/observability/logger.ts`, with request/correlation-id auto-attachment via `AsyncLocalStorage` and field-level redaction), Prometheus metrics (`src/lib/observability/metrics.ts`, new `prom-client` dependency — CPU/memory/API/DB/queue/errors/latency/business events, scraped via bearer-token-gated `GET /api/metrics`), request/correlation-id tracing (generated in `proxy.ts`, threaded through `withProtection` and into queue jobs), a liveness/readiness split (`GET /api/health/live`, `GET /api/health/ready`, alongside the existing combined `/api/health`), and critical-error alerting (`src/lib/observability/alerts.ts`, `ALERT_WEBHOOK_URL`, same unconfigured-by-default pattern as the existing SIEM webhook). **Two real bugs found and fixed during live-verification of the phase's own new code, not the app it was auditing**: (1) Next.js compiles each route into its own module bundle, so a plain module-level Prometheus registry / `AsyncLocalStorage` silently became a *different object* per route — metrics incremented in one route's bundle were invisible when scraped from another; fixed by caching them on `globalThis`, the same pattern `src/lib/db.ts` already used for the Prisma client. (2) that investigation surfaced that `db.ts`'s Prisma query-event listener was being re-attached once per bundle that imported it, N-multiplying the query counter; fixed with a `WeakSet`-per-instance guard. Also fixed while live-verifying: `logEnvStatus()` was fully built but never called anywhere (wired via new `src/instrumentation.ts`); `GET /api/leads` had no `withProtection` at all (no rate limiting, no metrics); the dev-mode email/SMS console fallbacks logged full message bodies + recipient PII with no production guard. **Found, deliberately not fixed**: 58 other bespoke GET routes have the same missing-`withProtection` gap as `leads` — same class of issue Phase 08 fixed for the 91 CRUD-factory domains, catalogued as the top follow-up for complete metrics/tracing coverage.

**Update 2026-09-06 (Phase 14 — Search, Reporting & Analytics)**: full audit (`SEARCH-REPORTING-ANALYTICS.md`) covering the search engine, the 6 requested report categories, permission-awareness, export, and unbounded-query risk. **Headline finding**: `GET /api/queue` (platform-wide job-queue status, an Operational report surfaced in `super-admin-view.tsx`) had zero authorization of any kind — any authenticated user of any tenant could see every job across the entire platform; now requires `isSuperAdmin()`. Also fixed 2 IDORs in `GET /api/reports` (an unauthorized `?audience=admin` request was honored instead of downgraded; `?scopeId=<any distributor>` was trusted from any caller instead of only a superadmin) and 7 previously-unbounded `findMany` calls (added `take`/`orderBy` caps). Confirmed-intentional, not changed after checking actual callers: `llm/providers`/`llm/audit` GETs stay readable by every tenant (their sole caller, `llm-settings-view.tsx`, is deliberately ungated — shared AI infra status, no secrets exposed). Shipped CSV/PDF export (`src/lib/export/`, new `pdfkit` dependency) on `leads` and `reports`; enhanced `leads` search to match across 4 fields instead of just `name`, plus real pagination. Deliberately not attempted: true FTS5 full-text search (blocked on `adr/0006`'s missing migration system) and Excel/.xlsx export (CSV already covers the practical need). One near-miss self-caught and reverted: capping `finance/reports`'s aggregation `findMany` with `take` would have silently truncated financial totals on wide date ranges — left unbounded with the correct fix (`db.aggregate()`/`groupBy()`) documented as deferred instead.

**Update 2026-09-06 (Phase 12 — Business Workflow)**: full workflow audit (`WORKFLOW-AUDIT.md`) — 18 stateful business processes catalogued; most had a `status` field writable to any client-sent string with no transition check. **Update 2026-09-06 (Phase 11 — AI/ML)**: full AI-stack audit (`AI-STACK-AUDIT.md`; no traditional ML pipeline exists, so this covers the LLM stack).
