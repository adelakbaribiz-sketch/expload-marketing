# BUSINESS-RULES.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Every rule below is quoted or paraphrased directly from the actual code implementing it (not from docs alone — several rules here correct or refine what `worklog.md`/`TECHNICAL_SPECIFICATION.md` state, where the code has diverged from or was never fully wired to the original design). Each rule states whether it is **live/enforced** or **defined but dead**.

---

## 1. Multi-tenancy & data lifecycle

- **Rule**: A `Tenant` row cascades deletion to the large majority of its child data (77 of 89 direct relations use `onDelete: Cascade`); 9 relations (notably `Activity.user`, `EmailTemplate.creator`) instead `SetNull` — preserving the historical record of *who did what* even after the acting user is deleted, rather than deleting the audit trail with them. **Live** (schema-enforced by the database itself).
- **Rule**: Tenant context for a request resolves in priority order: (1) authenticated session's tenant, (2) `X-Tenant-ID` header, (3) `tenant-id` cookie — the header/cookie fallback exists to support external API-client access but is not paired with any API-key/credential check. **Live**, and the source of the cross-tenant access findings in `SECURITY-BASELINE.md`.

## 2. RBAC / permissions

- **Rule (role hierarchy)**: `super_admin` → `owner` → `admin` → `manager` → `editor` → `viewer`. `super_admin` (via `SuperAdmin` table) and `owner` (via `user.role`) both get unconditional full access. **Live.**
- **Rule (admin, boolean check)**: In `hasPermission()`, `admin` is allowed everything **except** permission strings starting with `team.` or `billing.`. **Live.**
- **Rule (admin, list check — inconsistent with the above)**: In the separate `getUserPermissions()` function, `admin`'s literal permission list is `['leads.*','campaigns.*','seo.*','ads.*','social.*','content.*','analytics.*','ai.*']` — a fixed allowlist, not "everything except team/billing." **These are two different, not-reconciled definitions of what "admin" means, both live in the same file, used in different call paths.** This is a real inconsistency to resolve, not just document.
- **Rule (manager)**: identical wildcard list to `admin`'s `getUserPermissions()` version, minus `ai.*`. **Live** (in the `getUserPermissions()` path only).
- **Rule (editor)**: read/create/update (never delete) on `leads`, `campaigns`, `content` only. **Live** (`getUserPermissions()` path).
- **Rule (viewer)**: read-only on `leads`, `campaigns`, `seo`, `ads`, `social`, `content`, `analytics`. **Live** (`getUserPermissions()` path).
- **Rule (custom roles)**: a tenant can define a `Role` with an arbitrary `RolePermission` set via the UI. **Defined but dead** — the session's `roleId` is never populated by `getCurrentUser()`, so no permission check ever actually consults a custom role. A custom role can be created and assigned and will have zero effect on what that user can do.

## 3. Negotiation Engine — 6-round automatic concession formula

All percentages below are computed against **the original (Round 0) proposal's price and delivery weeks**, not the previous round's — confirmed in code (`previousProposals.find(p => p.round === 0)`).

| Round | Name | Price | Timeline | Scope/terms |
|---|---|---|---|---|
| 0 | Initial | 100% | 100% | Full scope |
| 1 | MVP Fast-Track | **-15%** (`price × 0.85`) | **-30%** (`weeks × 0.70`, min 1 week) | "-20% scope" is a prompt label only, not numerically derived from anything |
| 2 | Economic | **-30%** (`price × 0.70`) | **+50%** (`weeks × 1.50`) | Cheaper tech/models, framed as a trade-off in the LLM prompt |
| 3 | Phased | Phase-1 start cost **-60%** (`price × 0.40`) | 3 phases | No formula for total 3-phase price — left entirely to the LLM |
| 4 | Revenue-Share | Upfront **-60%** (`price × 0.40`) | — | + 20% of monthly revenue for 18 months (both hardcoded) |
| 5 | Equity/Partnership | Upfront **-85%** (`price × 0.15`) | — | + 3% equity, 36-month vesting (both hardcoded) — final offer |

- **Rule**: Rejecting a proposal auto-advances to the next round and generates a new one; accepting at any round immediately closes the negotiation as `accepted`, skipping remaining rounds. **Live.**
- **Rule**: Every state transition is logged to `NegotiationAuditEvent`. **Live** — implies negotiation history is meant to be fully auditable, a real (if unwritten) compliance requirement.
- **Important caveat**: the numbers above only seed the **LLM's prompt instructions** ("target price: $X"). The actual price/timeline/features shown to the customer come from the LLM's JSON response, which is not validated against the formula — the persisted `savingsPercent`/`deliveryReductionPercent` labels are the *intended* discount, not a guarantee of what the LLM actually returned. Treat the table above as the design intent, not a hard contract enforced on the AI's output.

## 4. Payroll / internal revenue distribution

- **Rule (revenue split)**: `ownerShare = totalRevenue × 50%`, `staffPool = totalRevenue × 40%`, `reinvestment = totalRevenue × 10%`, `bonusPool = staffPool × 5%` (i.e. bonus is a slice *of* the staff pool, not a separate 5th bucket off total revenue — despite `bonusPoolPercent` being named like a peer of the other three). **Live**, config-editable defaults.
- **Rule (per-employee share)**: `weightedContribution = roleWeight × hoursWorked × performanceFactor`; `sharePercent = employee's weightedContribution / sum(all weightedContributions)`; `baseShare = distributablePool × sharePercent` where `distributablePool = staffPool − bonusPool`; `bonusAmount = bonusPool × sharePercent` (same ratio as base — despite being called a "bonus," it isn't performance-differentiated). **Live.**
- **Rule (role weights)**: `c_level: 3, vp: 2.5, director: 2, manager: 1.5, lead: 1.2, senior: 1, staff: 0.7`. **Live**, config-editable defaults.
- **Rule (hours source)**: employees linked to a `VirtualAssistant` record get real approved-timesheet hours for the period; other salaried employees default to a **flat 160 hours** regardless of actual attendance; anyone with 0 computed hours gets 0 share. **Live** — this means payroll accuracy for non-VA-linked staff currently depends entirely on this flat assumption, not real time data.
- **Rule (performanceFactor)**: multiplied into the weighted-contribution formula but is **hardcoded to 1.0** everywhere — despite `AssistantPerformance` existing as a model and a code comment saying it "could be calculated from performance reviews." **Defined but dead** — performance currently has zero effect on pay.
- **Rule (tax withholding)**: flat **10%** of gross, applied unconditionally. Code comment implies it should be configurable per jurisdiction; it isn't. **Live**, not actually configurable.
- **Rule (period workflow)**: draft → calculated → approved → paid.

## 5. Wholesale distribution

- **Rule (license issuance)**: a distributor purchasing a license package gets `count` unique license keys, each expiring `pkg.validityMonths` months from issuance. **Live.**
- **Rule (tier restriction)**: a license package may specify a `tierRestriction`; issuance is rejected (403) if it doesn't match the purchasing distributor's own tier. **Live.**
- **Rule (spend tracking)**: `distributor.totalLicensesPurchased` and `totalPaidToPlatform` increment on each purchase — **but `totalPaidToPlatform` increments by the package's flat `wholesalePrice`, not `wholesalePrice × count`.** This looks like a real calculation bug (a batch purchase of e.g. 500 licenses would record the price of one license, not the batch), not an intentional rule — flag for engineering review, don't treat as designed behavior.
- **Rule (payout amounts)**: **there is no formula anywhere computing `platformShare`/`distributorShare`.** `POST /api/distributors/payouts` persists whatever those two numbers the caller supplies, unvalidated. Whatever revenue-split percentage a distributor's contract specifies is not connected to any actual payout calculation.
- **Rule (wholesale discount)**: `DistributorContract.wholesaleDiscountPercent` (default 40%) is **stored and displayed only** — confirmed via repo-wide search that it is never multiplied against any price or payout anywhere. A contract can say "40% wholesale discount" and it has no computational effect on anything.

## 6. Customer loyalty club

- **Rule (tiers)**: 4 tiers — Bronze (level 1, $0 spend, 0 months, 0% discount), Silver (level 2, $500, 3 months, 10%, 3 free ad credits, 500 API bonus), Gold (level 3, $2,000, 6 months, 20%, 10 credits, 2,000 API bonus, priority support + early access), Platinum (level 4, $5,000, 12 months, 30%, 25 credits, 5,000 API bonus, priority support + early access). **Live.**
- **Rule (upgrade evaluation)**: tier is (re)evaluated **on every `GET /api/club/membership` call**, upgrading to the *highest* tier the member currently qualifies for (both `totalSpend` and `monthsActive` thresholds must be met). This is pull-based, not event-driven — a member who crosses a spend threshold is not upgraded until the next time their membership is fetched, not the instant they qualify. **Live.**
- **Rule**: no downgrade logic exists anywhere — a member who has qualified for a tier keeps it even if later activity would no longer justify it.
- **Rule (signup bonus)**: 100 points granted automatically on first membership creation. **Live.**

## 7. LLM aggregator

- **Rule (fallback order)**: static priority Groq → Cerebras → OpenRouter → Mistral → HuggingFace, but the **last successful provider is tried first** on the next call regardless of static order (sticky-success routing), as long as it isn't in cooldown. **Live.**
- **Rule (cooldown)**: a provider that rate-limits goes into a **5-minute** cooldown and is excluded from candidates until it expires. **Live.**
- **Rule (quota warning)**: fires at **80%** of daily usage. **Defined, but the "already warned today" dedup check has a type-string mismatch** (`quota_warning` vs. the actually-emitted `llm_quota_warning`) — meaning the intended "warn once per day" behavior likely re-fires on every call once ≥80%, rather than deduping as designed. Flag for engineering fix.
- **Rule (daily quota enforcement)**: default 1,000,000 tokens/day, **actually enforced** against usage.
- **Rule (monthly quota)**: default 10,000,000 tokens/month, **stored and settable via the UI but never read or checked anywhere in the aggregator** — completely unenforced despite appearing to be a real limit.

## 8. Support plans / SLA

- **Rule (response/resolution windows)**: Basic 48h response / 168h resolution; Premium 4h / 48h; Enterprise 1h / 8h.
- **Rule (deadline computation)**: `slaResponseDue`/`slaResolutionDue` are correctly computed and stamped on ticket creation, based on the customer's active subscription's plan (falling back to 48h if no active subscription). **Live at creation time.**
- **Rule (enforcement)**: **there is no code anywhere that checks a ticket against its SLA deadline** — no breach flag, no escalation, no overdue notification, no scheduled job. The fields exist and are correctly set, and then nothing ever reads them for enforcement purposes. This is a real, silent gap between what the feature implies (an enforced SLA) and what it does (a timestamp nobody checks).

## 9. Onboarding

- **Rule (step order, intended)**: `welcome → profile → goals → budget → team → first_lead → first_campaign → done` (one system) / a numeric 6-step wizard (a second, parallel system — `OnboardingSession.currentStep`/`totalSteps`).
- **Rule (sequencing enforcement)**: **none, in either system.** Both accept an arbitrary step/status value from the client with no check that prior steps were completed or that steps only advance by one. This is a purely client-trusted "honor system," not a server-enforced business rule, despite the data model implying a strict sequence.

## 10. Rate limiting

- **Rule (exact limits)**: `read`: 100 req/min · `write`: 30 req/min · `ai`: 10 req/min · `auth`: 5 req/min. **Live**, sliding-window, in-memory (single-process only — see `KNOWN-ISSUES.md` #13 for the scaling caveat).
- **Rule**: there is **no `public` rate-limit tier in code** — any documentation or plan referring to "public rate limiting" is describing a gap, not an existing rule (see `KNOWN-ISSUES.md` #12).

## 11. Campaign scheduling

- **Rule (event scoring, live fallback path)**: `score = (30 if high relevance else 15 if medium else 0) + (25 if industry matches) + (20 if campaign type matches) + max(0, 20 − daysUntilEvent)`, max possible 95, ranked descending. Primary path is LLM-generated suggestions; this formula is the deterministic fallback used only if the LLM response fails to parse as JSON.
- **Rule (fallback campaign duration)**: budget ≥$10,000 → 30 days; ≥$5,000 → 21 days; else 7 days (fallback path only — the LLM prompt instructs a richer 7/21/30-45 day + 1.2-1.5x impact-multiplier scheme that isn't guaranteed in the actual fallback code, which uses a fixed 1.3x multiplier).
