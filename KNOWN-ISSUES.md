# KNOWN-ISSUES.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Every item below is verified against actual code (file:line), not inferred. Ranked by real-world severity, factoring in that `src/proxy.ts` DOES gate every non-public route behind a valid session cookie — so "requires auth" below means "requires only a free self-signup account" (signup is public), not a privileged position, and "public/anonymous" means genuinely reachable with zero account.

Full technical detail and evidence for the security items is in `SECURITY-BASELINE.md`; this file is the prioritized punch list.

**Update 2026-09-05 (Phase 05 — Security Engineering)**: a full security-engineering pass (`THREAT-MODEL.md`, rewritten `SECURITY-BASELINE.md`, new `SECURITY.md`) audited authentication/authorization/RBAC/sessions/secrets/API/database/file-upload/storage/logs/CORS/CSRF/XSS/SQLi/SSRF/rate-limiting/brute-force/privilege-escalation/IDOR/sensitive-data-exposure/dependencies/container/cloud security. Found and fixed **14 Critical and 9 High** findings, live-verified where a running server was needed (see `scripts/security-checks.ts`, `bun run security-check`) — including a complete privilege-escalation chain (`team/members`/`team/invite/[token]`) that let any free-signup user take over an arbitrary existing account, a plaintext payment-gateway-secret leak (`GET /api/payments/gateways`) to any authenticated user, an SSRF in the onboarding website crawler, and direct public exposure of Postgres/Redis/the app itself caused by `docker-compose.prod.yml`'s port publishing (which also made the login rate-limiter's IP-trust bypassable). Item #12 and #13 below are now fixed as part of this pass — see their entries. Full per-finding detail is in `SECURITY-BASELINE.md`, not duplicated here.

## Critical

1. ~~**`POST /api/seed` is public...**~~ **FIXED** (2026-09-04). Now requires authentication, removed from `proxy.ts`'s public allowlist, rate-limited via `withProtection`, and no longer returns the plaintext password in its response. Verified live: an anonymous call now gets 401 at the proxy layer before even reaching the route. The one real caller (`page.tsx`'s auto-bootstrap effect, which already only fires post-login) still works. See `docs/IMPLEMENTATION-PLAN.md` #1.

2. ~~**Support-plan tickets and subscriptions can be read/modified/cancelled cross-tenant...**~~ **FIXED** (2026-09-04). Both PATCH handlers now fetch the existing record first and 404 if its `tenantId` doesn't match the caller's. Verified live with a real cross-tenant attack simulation: a second tenant's ticket returned 404 to the wrong caller, 200 to the right one. See `docs/IMPLEMENTATION-PLAN.md` #2-3.

## High

3. ~~**`requireTenantId()` falls back to a caller-supplied `X-Tenant-ID` header or `tenant-id` cookie...**~~ **FIXED** (2026-09-04), with a revised design from the original recommendation — see `docs/IMPLEMENTATION-PLAN.md`'s dependency-check section: the `tenant-id` cookie turned out to be a real, live feature (the sidebar's tenant-switcher for SuperAdmins, via `providers.tsx`'s `TenantSync`), not dead weight, so instead of removing it outright, `getTenantId()` now only honors that cookie override when the caller is a real, authenticated SuperAdmin — every other user always resolves to their own session tenant, full stop. The `X-Tenant-ID` header fallback (confirmed zero legitimate callers anywhere in the app) was removed outright. Verified live: a non-superadmin's forged `tenant-id` cookie is now ignored; a superadmin's genuine tenant-switch still works correctly. See `adr/0004` (status updated to Accepted).

4. ~~**`GET /api/tenants` has no auth check...**~~ **FIXED** (2026-09-04). Now requires authentication; non-superadmins get only their own tenant, superadmins keep the full list (needed for the switcher above). `POST` now also requires authentication. Verified live.

5. ~~**`PATCH`/`DELETE /api/marketplace/products/[id]` have no auth check...**~~ **FIXED** (2026-09-04). Both now require SuperAdmin (the model has no `tenantId` — it's platform-global, so platform-operator-only is the correct scope). Verified live: non-superadmin now gets 403. No frontend caller existed for this endpoint, so nothing else changed behavior.

6. ~~**`POST /api/leads/[id]/enrich` and `POST /api/campaigns/[id]/send` take no ownership check...**~~ **FIXED** (2026-09-04). Both now require authentication and verify the referenced lead/campaign's `tenantId` matches the caller's before acting; `leads/[id]/enrich` also gained rate limiting (`ai` preset) it didn't have before. Verified live with real cross-tenant attempts on both routes — both correctly 404.

7. **11 of 15 configured payment gateways are non-functional stubs that appear to work.** `src/lib/payment/gateway-router.ts` (explicitly commented "stubs — wire to real SDKs in production") — Stripe, PayPal, Razorpay, Moyasar, Paystack, Flutterwave, Tap, HyperPay, Mollie, Midtrans, and Iyzico all return fabricated reference strings/URLs with zero outbound HTTP calls to the real provider. Only NOWPayments (crypto) is real. **Risk**: if this ships to a real customer believing card payments work, money is never actually charged/captured while the UI reports success. **Fix**: either implement the real SDK calls before enabling these gateways in any environment where customers could select them, or hide them from the UI until they are, whichever comes first.

8. **Four "analyzer" features silently fabricate results instead of doing real analysis, indistinguishably from real output.** `POST /api/backlinks/discover`, `POST /api/competitor-analysis/run`, `POST /api/analyzers/social/analyze`, `POST /api/seo/[id]/crawl` all unconditionally generate `Math.random()`-based data and persist it to the database as if it were a real crawl/API result — not gated behind "no provider configured," they never do real analysis regardless of configuration. A customer relying on these numbers for a real business decision would be acting on fiction. **Fix**: either wire real providers (Ahrefs/SEMrush-class APIs, a real crawler) or clearly label these outputs as simulated/demo-only in the UI until they are.

## Medium

9. ~~**Sessions never expire server-side...**~~ **PARTIALLY FIXED** (2026-09-04, `adr/0007` step 1): the session token now carries a signed `issuedAt` claim, and `verifySessionToken` (plus `proxy.ts`'s mirrored Edge-runtime check) rejects any token older than 30 days server-side, not just via the browser-side cookie hint. Verified live: signup/login/session-check all work correctly with the new 3-part token format. **Still open**: no per-user revocation list yet (`adr/0007` step 2) — logout still only clears the client cookie; a leaked-but-not-yet-30-days-old token remains valid if replayed. Step 2 deferred, not implemented this pass (see `docs/IMPLEMENTATION-PLAN.md`).

10. **~96% of API routes accept unvalidated request bodies.** Only 9 of 239 route files import `zod`. The generic CRUD factory (`src/lib/crud/domain-handler.ts`) validates field *names* via an allowlist but not types/formats/enums. No SQL-injection risk (Prisma parameterizes) and XSS is mitigated by `sanitizeText()` on string fields, but there's no data-integrity guarantee — malformed types, out-of-range values, or missing required fields can silently corrupt records or produce confusing Prisma errors instead of clean 400s. **Fix**: prioritize adding zod schemas to the CRUD factory itself (would cover ~46 domains at once) before doing it route-by-route on the ~140 remaining bespoke routes.

11. **Production CSP allows `script-src 'self' 'unsafe-inline'`.** `src/proxy.ts` and `src/lib/security/headers.ts` (two independent, hand-synced copies of the same header logic). This materially weakens CSP as an XSS mitigation — the rest of the policy is reasonably tight (`object-src 'none'`, `frame-ancestors 'none'`, scoped `connect-src`). **Fix**: move to a nonce- or hash-based `script-src` when there's time to test it against every inline script in the app; low urgency absent a known XSS to pair it with, but worth scheduling.

12. ~~**Public, unauthenticated endpoints have no rate limiting...**~~ **FIXED** (2026-09-05). New `public` rate-limit preset (20/min) added and applied to `/api/sandbox/{start,action,convert}`, `/api/public/demo`, `/api/public/pricing-calculate`, and `/api/team/invite/[token]` (GET+POST). See `SECURITY-BASELINE.md` §18.

13. ~~**The rate limiter is in-memory and single-process**... `getClientId()` trusts `X-Forwarded-For` unconditionally... would be spoofable if... exposed directly (the prod compose does publish port 3000 to the host).~~ **The X-Forwarded-For spoofing bypass is FIXED** (2026-09-05) — `docker-compose.prod.yml`'s app service now binds `127.0.0.1:3000:3000` instead of the default `0.0.0.0`, closing the direct-exposure path that made this exploitable (confirmed real: Postgres/Redis were *also* published directly to the host, now removed too — see `SECURITY-BASELINE.md` §25). The in-memory/single-process nature itself remains an accepted limitation until horizontal scaling is actually planned (would need a Redis-backed store at that point) — not urgent today.

14. **Two disconnected AI stacks** — the documented multi-provider LLM aggregator vs. `z-ai-web-dev-sdk`, the latter with no configurable env var and a code comment indicating it's coupled to a specific original sandbox environment. Several AI-adjacent features (lead enrichment quality, diagnostics, monthly AI reports) will silently run on rule-based fallback logic rather than a real LLM in any self-hosted deployment, with no visible warning to the operator that this is happening. **Fix**: either replace these call sites with the aggregator, or make the SDK dependency's environment requirement explicit in `.env.example`/`README-DEPLOY.md` so operators know these features need something the current docs don't mention.

15. **WhatsApp and SMS have full CRUD data models and dashboard UI but no outbound send integration to any real provider anywhere in the codebase.** A user creating a "WhatsApp message" or "SMS message" through the UI gets a successfully-saved database row and no indication that nothing was actually sent. **Fix**: either integrate a real provider (WhatsApp Business API, Twilio/Kavenegar for SMS) or add a clear "not yet connected" state in the UI so this isn't mistaken for a working feature.

16. **Deploy-path defects**: (a) `README-DEPLOY.md` and `scripts/dev-setup.sh` both call `bun run db:seed`, which does not exist in `package.json` — this documented setup step fails as written. (b) `scripts/deploy.sh` runs `prisma migrate deploy`, but no `prisma/migrations/` directory exists in the repo, so this is a no-op against a fresh database (`scripts/deploy-vps.sh` hedges with a `db push` fallback; `deploy.sh` does not). (c) `README-DEPLOY.md`'s documented default login (`admin@expload.io` / `admin123`) does not match the actual hardcoded seed password in code (`demo12345`). **Fix**: either add a real `db:seed` script (chaining the existing standalone seed scripts), initialize `prisma/migrations/` and switch the deploy scripts to a consistent migrate-or-push strategy, and correct the README password — or decide the seed-route approach is being retired (see #1) and rewrite this section of the deploy docs around `bootstrap-super-admin.ts` instead.

## Low / Info

17. `README.md` is still the unmodified `create-next-app` boilerplate — misleading to a first-time reader; the real docs (`README-DEPLOY.md`, `TECHNICAL_SPECIFICATION.md`) aren't linked from it.
18. `next dev` (Turbopack, the default) has a known-and-already-documented `@prisma/client` resolution bug in this project; `next dev --webpack` is the working path. Already documented in `README-DEPLOY.md`'s troubleshooting section — just worth keeping visible until upstream fixes it.
19. Password-reset pages (`/forgot-password`, `/reset-password`) are listed as public routes but no corresponding API route exists anywhere under `src/app/api` — these pages, if they render at all, have no working backend.
20. `bun run build`'s `cp -r` step fails under Bun's own `--shell=bun` script runner in some environments (observed directly this session) but works via a POSIX shell — environment quirk, not a code defect; worth a one-line troubleshooting note.
