# ACCEPTANCE-CRITERIA.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Given/When/Then criteria for the core flows in `USE-CASES.md`, plus cross-cutting criteria for multi-tenancy and authorization. Since **no automated test suite exists in this project** (`TECH-STACK.md`), this document doubles as the closest thing to a test specification currently available — each criterion is written so it could become a test case directly. Criteria are marked ✅ (currently met, verified this audit), 🔴 (currently NOT met — a real defect, cross-referenced to `KNOWN-ISSUES.md`), or 🟡 (partially met / not independently verified this pass).

---

## AC-1: Tenant Signup

- ✅ **Given** a visitor submits a valid name/email/8+ char password/tenant name/domain, **when** they submit signup, **then** a new isolated tenant and an owner-role user are created and the visitor is logged in automatically.
- ✅ **Given** a new tenant was just created, **when** the owner views their dashboard, **then** sample leads, a default funnel, a welcome journey, fraud rules, and club enrollment already exist (not an empty state).
- ✅ **Given** a domain is already registered to another tenant, **when** signup is attempted with that domain, **then** signup is rejected with a 400.
- 🔴 **Given** an anonymous caller with no account, **when** they `POST /api/seed`, **then** — this should not be possible in production at all; currently it creates/resets a known account and returns its password in plaintext. See `KNOWN-ISSUES.md` #1.

## AC-2: Team Invite & Acceptance

- ✅ **Given** an owner invites `new@example.com` with role "editor", **when** the invitee opens the invite link and submits a name+password, **then** a new account is created in the inviter's tenant with role "editor" and the invitee is logged in.
- ✅ **Given** an invited email already has an account elsewhere, **when** that person accepts the invite, **then** their existing account's tenant/role is reassigned to the inviting tenant.
- ✅ **Given** an invitation is older than 7 days, **when** the link is opened, **then** it shows an expired state and cannot be accepted.
- 🟡 **Given** the existing-account acceptance path requires no password re-entry, **when** someone other than the true owner of that email possesses the invite link, **then** they could accept on that email's behalf — acceptable only because the token itself (sent out-of-band) is the intended secret; flagged for awareness, not necessarily a defect.

## AC-3: Multi-Tenancy Isolation (cross-cutting — the platform's core promise)

- 🔴 **Given** User A (tenant 1) and a support ticket belonging to tenant 2, **when** User A calls `PATCH /api/support-plans/tickets` with tenant 2's ticket id, **then** the request should be rejected — **currently it succeeds**. See `KNOWN-ISSUES.md` #2 (Critical).
- 🔴 **Given** any signed-up user, **when** they call `GET /api/tenants`, **then** they should see only their own tenant — **currently they see every tenant's id/name/domain/plan/counts**. See `KNOWN-ISSUES.md` #4.
- 🔴 **Given** any signed-up user, **when** they send `X-Tenant-ID: <another tenant's id>` on a request whose session has become invalid (e.g. a deactivated account) but is still cryptographically well-formed, **then** the request should 401 — **currently it's honored, granting that tenant's context**. See `KNOWN-ISSUES.md` #3.
- ✅ **Given** a route built on the generic CRUD factory with a *valid, active* session, **when** a user requests a record belonging to another tenant by id, **then** it correctly 404s (the fetch-then-compare ownership check works for the common case).
- 🔴 **Given** any signed-up user, **when** they `PATCH`/`DELETE /api/marketplace/products/[id]` for a product they don't own, **then** it should be rejected — **currently it succeeds**. See `KNOWN-ISSUES.md` #5.

## AC-4: Negotiation Engine

- ✅ **Given** an onboarding session with business context, **when** negotiation starts, **then** a Round 0 proposal is generated reflecting full scope/price/timeline.
- ✅ **Given** a Round 0 proposal is rejected, **when** the system generates the next proposal, **then** it targets the LLM at approximately 15% lower price and 30% shorter timeline (MVP terms) — **not guaranteed exact**, since the LLM's actual output isn't validated against the target.
- ✅ **Given** any round's proposal is accepted, **when** the customer accepts, **then** the negotiation immediately closes as `accepted` regardless of which round it's on.
- ✅ **Given** Round 5 (Equity) is rejected, **when** the system processes the rejection, **then** the negotiation closes as `rejected_all` with no further automatic proposal.
- ✅ **Given** any state transition occurs, **when** it happens, **then** a corresponding `NegotiationAuditEvent` is persisted.

## AC-5: Payroll Run

- ✅ **Given** `totalRevenue = $100,000` and default config, **when** payroll runs, **then** `ownerShare = $50,000`, `staffPool = $40,000`, `reinvestment = $10,000`, `bonusPool = $2,000` (5% of the $40,000 staff pool, not of total revenue).
- ✅ **Given** two employees with equal hours but different role weights (e.g. manager 1.5 vs. staff 0.7), **when** payroll runs, **then** the manager's share is proportionally larger by the weight ratio.
- 🔴 **Given** two employees with identical weight/hours but very different actual performance, **when** payroll runs, **then** their pay should differ if performance is meant to matter — **currently it never does**, since `performanceFactor` is hardcoded to 1.0. See `BUSINESS-RULES.md` §4.
- 🟡 **Given** a salaried, non-VA-linked employee, **when** payroll computes their hours, **then** it should reflect actual attendance — **currently it assumes a flat 160 hours regardless of reality**.

## AC-6: Support Plan SLA

- ✅ **Given** a tenant with an active Premium subscription, **when** they submit a ticket, **then** `slaResponseDue` is set to 4 hours from creation and `slaResolutionDue` to 48 hours.
- 🔴 **Given** a ticket's `slaResponseDue` has passed with no agent response, **when** that deadline is crossed, **then** the system should flag/escalate it — **currently nothing happens; no code anywhere checks this.** See `BUSINESS-RULES.md` §8.

## AC-7: Custom Role Permissions

- 🔴 **Given** an owner creates a custom role restricting a user to read-only access, **when** that user attempts a write action, **then** it should be denied — **currently it is allowed**, because the permission check never reads the custom role at all (`roleId` isn't populated on the session). See `KNOWN-ISSUES.md` / `BUSINESS-RULES.md` §2. This is arguably the most user-visible gap in the whole audit: the feature *appears* to work (the UI saves the role, assigns it, shows it) with no error, and silently does nothing.

## AC-8: Payment Gateways

- ✅ **Given** a tenant sends a crypto payment via NOWPayments, **when** the payment completes, **then** the inbound webhook's signature is verified (HMAC-SHA512) and the payment is recorded.
- 🔴 **Given** a tenant "configures" Stripe with a real secret key, **when** a customer attempts to pay by card, **then** a real charge should be created — **currently no HTTP call to Stripe happens at all**; the returned `clientSecret` contains the literal string `_mock`. See `KNOWN-ISSUES.md` #7. The same applies to the other 10 non-crypto gateways.

## AC-9: LLM Aggregator

- ✅ **Given** the primary LLM provider rate-limits a request, **when** the aggregator retries, **then** it automatically falls back to the next available provider and the response still succeeds (assuming at least one provider is healthy).
- ✅ **Given** a provider enters cooldown after a rate-limit, **when** 5 minutes have not yet passed, **then** it's excluded from candidate selection.
- ✅ **Given** a provider succeeded on the last call, **when** the next call is made, **then** that same provider is tried first, ahead of the static priority order.
- 🔴 **Given** a provider crosses 80% of its daily quota, **when** subsequent calls are made that day, **then** a single warning notification should fire once — **currently the "already warned" dedup check references a mismatched event-type string and likely re-fires on every call.** See `BUSINESS-RULES.md` §7.
- 🔴 **Given** `monthlyTokenLimit` is configured on a provider, **when** monthly usage exceeds it, **then** the provider should stop being used — **currently monthly usage is never checked at all**, only daily.

## AC-10: Onboarding Wizard Sequencing

- 🔴 **Given** a user has completed only step 1 of 6, **when** they (or a malicious client) directly submit step 6 as complete, **then** the system should reject it as out-of-sequence — **currently it's accepted with no validation.** See `BUSINESS-RULES.md` §9.

## AC-11: Distributor Payouts

- 🔴 **Given** a distributor's contract specifies a wholesale discount and commission terms, **when** a payout is requested, **then** the payout amount should be computed from those terms — **currently the amount is whatever the caller supplies, with no formula connecting it to the contract at all.** See `KNOWN-ISSUES.md` and `BUSINESS-RULES.md` §5.
- 🔴 **Given** a distributor purchases 500 licenses at a package's wholesale price, **when** `totalPaidToPlatform` is updated, **then** it should increase by `price × 500` — **currently it increases by the flat single-package price regardless of quantity**, a likely real calculation bug.

## AC-12: Rate Limiting & Anonymous Endpoints

- ✅ **Given** 6 login attempts in one minute from the same client, **when** the 6th is made, **then** it is rejected (auth limit is 5/min).
- 🔴 **Given** an anonymous caller repeatedly calls `POST /api/seed` or `POST /api/sandbox/start`, **when** they do so faster than any reasonable human rate, **then** they should be throttled — **currently neither route has any rate limit at all.** See `KNOWN-ISSUES.md` #12.
