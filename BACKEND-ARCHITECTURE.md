# Backend Architecture — Phase 08 (Backend Engineering)

**Date**: 2026-09-04
**Scope**: Audit + standardization of the Next.js 16 API layer (`src/app/api/**`, 239 route files) and its supporting `src/lib/**` modules. Companion to `DATABASE-AUDIT.md`/`DATABASE-TARGET.md` (Phase 04), `THREAT-MODEL.md`/`SECURITY-BASELINE.md` (Phase 05), and `DESIGN-SYSTEM.md` (Phase 07).

Audited via three full-codebase sweeps (business-logic placement, cross-cutting concerns, background-jobs/events/authorization) plus direct reads of the central infrastructure files. This document is the synthesis: current layering, findings per area, what was fixed now, and what's deferred with severity.

---

## 1. Current layering

There is no formal API/Application/Domain/Infrastructure split. In practice, three layers exist informally:

- **Route handlers** (`src/app/api/**/route.ts`, 239 files) — the only entry point; Next.js route convention.
  - **91 files** are generated by the generic CRUD factory (`src/lib/crud/domain-handler.ts`'s `createDomainHandlers`/`createDomainItemHandlers`) — a real, reused, model-agnostic abstraction (confirmed: no `if (config.model === 'X')` branching).
  - **148 files** are bespoke, hand-written handlers.
- **Service modules** (`src/lib/<domain>/*`) — exist for `ai`, `auth`, `campaign-scheduler`, `crud`, `decision-engine`, `email`, `events-calendar`, `finance`, `graph`, `llm`, `negotiation`, `notifications`, `onboarding`, `payment`, `project-intake`, `queue`, `security`, `services`, `vector`, and (new this phase) `billing`, `club`. **No service module exists** for `payroll`, `distributors`, `attribution` (fraud-rule logic is 100% CRUD-factory, not bespoke), `pricing` (pre-existing this phase), `commissions`, `marketplace`, `white-label`, `promo-links`, `autonomous-agent`/`agent`, or `progressive`. Where a bespoke route in one of those domains has real business logic, it has nowhere else to live — it's inline in the controller by construction, not by neglect.
- **Prisma models** (`prisma/schema.prisma`) — the only "domain" layer; no repository abstraction, which is fine at this scale (see `adr/0001`, modular monolith).

This shape is reasonable for a monolith this size. The problems below are less "wrong architecture" and more "no shared conventions were ever established for the concerns that cut across every route" — each of the 148 bespoke files independently reinvented validation, error handling, and (for a handful) financial calculations.

## 2. Business Logic placement

**Audit finding** (full methodology and file-by-file breakdown in the phase's research agent output — summarized here): of 148 bespoke route files, roughly 55-60 are clean (thin controller, real delegation), 55-60 are "light" (minor inline logic, acceptable), and ~20-30 are "heavy" — real financial/state-machine/AI-orchestration logic embedded directly in the controller. Every file over 120 lines except two (a fixtures-only demo route and a dev-seed script) turned out to embed non-trivial business logic, concentrated almost entirely in the domains with no service module (see §1).

**Ranked worst offenders** (money/multi-tenant-integrity risk first):

1. `payroll/run/route.ts` — full revenue-split algorithm (50/40/10, weighted contribution formula, bonus pool, tax withholding) inline.
2. `club/membership/route.ts` — GET auto-provisions membership/tiers/rewards (a read path doing first-run seeding) and runs a tier-upgrade state machine inline.
3. `club/rewards/[id]/redeem/route.ts` — point-redemption logic with a TOCTOU race (fixed this phase, see §4).
4. `distributors/licenses/route.ts` — license-key issuance with an unbounded client-supplied `count` (fixed this phase, see §4) and 4 non-transactional writes (fixed, see §4).
5. `distributors/payouts/route.ts` — **not fixed this phase**: `distributorShare` is taken verbatim from the request body with zero server-side computation against the distributor's actual commission rate. Flagged, deferred — needs a product decision on the payout formula before a fix can be written (mirrors the gap `adr/0003` originally called out).
6. `distributors/route.ts` / `white-label/customers/route.ts` — orphaned-tenant risk on a two-step create (fixed this phase, see §4).
7. `auth/signup/route.ts` — 10-step inline tenant-provisioning workflow wrapped in one broad try/catch that silently swallows failures ("non-fatal"), leaving a tenant permanently half-initialized. **Duplicated near-verbatim** in `quick-setup/route.ts` (~150 lines, independently maintained, divergent idempotency). **Not consolidated this phase** — real risk, but consolidating two live provisioning paths needs its own careful pass (both are exercised by production-shaped flows); documented as a high-priority deferred item.
8. `billing/calculate/route.ts` + `public/pricing-calculate/route.ts` + `billing/subscription/route.ts` — three independent copies of the plan-scoring/ROI algorithm and the plan/feature-limits table. **Fixed this phase**: extracted to `src/lib/billing/pricing-engine.ts` (see §4).
9. `finance/reports/route.ts` — a cruder duplicate of the real `src/lib/finance/reports.ts` engine (used correctly by exactly one other route, `reports/route.ts`). Two endpoints, same purpose, different metric shapes, writing to the same `FinancialReport` model. **Not consolidated this phase** — needs a decision on which one is canonical; documented as deferred.
10. `agent/run/route.ts` (250 lines) / `progressive/route.ts` (252 lines, the largest bespoke file in the codebase) — full autonomous-agent cycle logic and full plan-tier feature-gating state machine, both entirely inline with no service module. Both are legitimate future extraction targets; out of scope for this phase's fix budget.
11. `diagnostics/run/route.ts` / `reports/monthly/generate/route.ts` — duplicated manual LLM-JSON-extraction (`indexOf('{')`/`lastIndexOf('}')`) despite a shared `parseJsonResponse()` already existing and being used correctly elsewhere. **Fixed this phase** (see §4).
12. `ecommerce/profit-calculator/route.ts` — real inline financial calculator with a confirmed live bug (a module-scope `let competitionLevel` declared *after* the handler that references it, so it was always `null` — the "competition" recommendation branch was permanently dead). **Fixed this phase** (see §4).
13. `platform/referrals/route.ts` — hardcoded `$50`-per-referral total while `ReferralProgram.referrerReward` is a configurable field. **Fixed this phase** (see §4).

**Duplicated business logic** (beyond the pricing/LLM-parse cases already listed): the club-tier definitions (Bronze/Silver/Gold/Platinum) are hardcoded identically in three places (`auth/signup`'s auto-setup, `quick-setup/route.ts`, `club/membership/route.ts`'s `createDefaultTiers()`); the `PLATFORM_FEES` marketplace-fee table is duplicated between `ecommerce/profit-calculator` and `ecommerce/analyze`.

**What shipped this phase**: the 5 items marked "Fixed this phase" above, plus wrapping the club-rewards-redeem transaction logic in a small extracted service (`src/lib/club/redeem-reward.ts`) as a worked example of pulling business logic out of a controller and making it independently testable — see §9.

**Deferred** (documented, not fixed — each needs either a product decision or a larger dedicated pass): distributor-payout formula, signup/quick-setup consolidation, finance/reports dual-implementation reconciliation, `agent/run` and `progressive` service extraction.

## 3. Validation

**Finding**: only 10 of 239 route files use zod (`auth/login`, `auth/signup`, `campaigns`, `leads`, `projects`, `sandbox/convert`, `team/invite/[token]`, `team/invite`, `templates`, `tenants`). No shared validation helper exists anywhere in `src/lib`. Outside those 10 files, validation ranges from a single manual `if` check to none at all — `req.json()` values flow straight into Prisma `data:` objects across most of the 138 bespoke non-zod routes, and all 91 CRUD-factory routes validate only that submitted field *names* are in an allowlist (`DomainConfig.fields`), with no type/format/enum checking.

**What shipped this phase**: `DomainConfig` gained an optional `validate` hook (adr/0003, implemented — see §9) so any factory domain can now adopt a zod schema without special-casing the factory. Two live crash risks were closed with minimal guards: `internal/employees` POST no longer throws a raw `TypeError` on a missing `email` (now a clean 400), and `distributors/route.ts`/`white-label/customers/route.ts` POST now require `companyName`/`customerName` before starting a transaction. `distributors/licenses/route.ts`'s client-supplied `count` is now bounds-checked (integer, 1-1000) — it was previously unbounded, a real resource-exhaustion / negative-count risk.

**Deferred**: rolling zod (or the new `validate` hook) out across the remaining ~128 unvalidated bespoke routes and 91 CRUD-factory domains. This is real, systemic, and large — appropriately a dedicated future pass (or done incrementally per-domain as each is touched), not a single-phase mechanical rewrite of ~220 files. Prioritize by risk: money-handling and multi-tenant-write routes first (payroll, club, distributors, marketplace, internal — several already covered by this phase's transaction/guard fixes; validation is the next layer).

## 4. Transactions

**Finding**: `src/lib/payment/crypto.ts` (fixed in Phase 04) was the only `$transaction` call in `src/` at the start of this phase. Confirmed still-missing transactions across 7 known routes (`DATABASE-TARGET.md` DB-08) plus one newly found this phase (`internal/employees`), all multi-step writes with no atomicity:

| Route | Risk | Status |
|---|---|---|
| `payroll/run` | Partial payroll: period created, salary-payment loop fails partway through | **Fixed** — wrapped in `$transaction` |
| `distributors/licenses` | License keys issued but financial totals (`distributor`/`licensePackage`) not updated on failure | **Fixed** — wrapped in `$transaction`; `count` also bounds-checked |
| `club/rewards/[id]/redeem` | TOCTOU race: check-then-decrement on `availablePoints`, concurrent redemptions could double-spend | **Fixed** — atomic `updateMany` guard (`gte` condition) inside `$transaction`; extracted to `src/lib/club/redeem-reward.ts` |
| `club/membership` (`create_ad` action) | Same TOCTOU race on `adCreditsBalance` | **Fixed** — same atomic-guard pattern |
| `distributors/route.ts` POST | `tenant.create` + `distributor.create`, failure between them orphans the tenant | **Fixed** — wrapped in `$transaction` |
| `white-label/customers/route.ts` POST | Same orphaned-tenant risk (`tenant.create` + `resellerCustomer.create`) | **Fixed** — wrapped in `$transaction` |
| `team/invite/route.ts` | Invitation created with no matching audit-log entry on failure | **Fixed** — wrapped in `$transaction` |
| `internal/employees` POST (newly found) | Up to 3 sequential writes (tenant+user, employee, activity log) | **Fixed** — wrapped in `$transaction` |

All 8 fixes follow the same pattern already established and live-verified in Phase 04's crypto-payment fix: a `db.$transaction(async (tx) => {...})` wrapping the sequential writes, with a code comment explaining the specific race/partial-write risk it closes. The two check-then-act race fixes (club rewards/ads) additionally use a `WHERE ... AND balance >= cost` guard on the `updateMany` so a losing concurrent request fails cleanly instead of overdrawing — this is now integration-tested (see §9) with a real concurrent-redemption test against the dev database.

**Deferred**: `adr/0006` (adopting real Prisma migrations, the mechanism `$transaction` fixes ride on in production) remains the longest-standing deferred item, unrelated to this phase's scope.

## 5. Error Handling

**Finding**: no shared error-handling wrapper existed. `withProtection()` called the wrapped handler with no try/catch, so an uncaught exception propagated to Next.js's generic 500 (no security headers, no rate-limit headers, no consistent shape). The CRUD factory itself had zero try/catch in any of its 4 functions. Error response shapes were wildly inconsistent where they existed at all: plain `{ error: string }` (289 occurrences, mostly hand-checked branches), `{ error: err.message }` (leaks raw exception text), `{ error: 'llm_failed', message }` (different key set), a zod-flatten object under the same `error` key as everywhere else's plain string, an error embedded in a 201-status "success" response (`negotiation/sessions` POST), and silent-swallow-no-error-surfaced (`auth/signup`'s auto-setup, `diagnostics/run`, `reports/monthly/generate`). Roughly 169 of 239 route files (71%) had **no** try/catch anywhere, including all 91 CRUD-factory routes.

**What shipped this phase**:
- `withProtection()` (`src/lib/security/with-protection.ts`) now wraps the handler call in try/catch. An uncaught exception is logged (`console.error('[api] unhandled error:', err)`) and converted to a clean `NextResponse.json({ error }, { status })` — still carrying security headers and rate-limit headers, which previously only applied to a successful response.
- A new `ApiError` class (`src/lib/api/errors.ts`) lets a handler — including code running inside a `db.$transaction` callback, where returning a `NextResponse` isn't an option — throw with a specific status and message instead of falling through to a generic 500. Used by the CRUD factory's `getItem`/`patchItem`/`deleteItem` (404 on not-found) and the two transaction-guard fixes in §4 (409/400 on a lost race).
- The CRUD factory's GET handlers are now wrapped in `withProtection` too (see §8) — previously they had **no** protection layer at all, so they couldn't even reach a catch block; every list/read endpoint across 91 domains now gets consistent error handling for free.

This is additive and backward-compatible: every route that already returns its own `{ error }` response on an expected condition (bad input, permission denied, not found) is unaffected — the new catch only fires for something that would otherwise have crashed the request.

**Deferred**: standardizing the *existing* hand-written `{ error }` shapes across the 289 call sites that already return one is a larger, lower-urgency cleanup (they're inconsistent in field names but none of them crash) — not attempted this phase. A structured logger (see §6) to replace the new `console.error('[api] ...')` calls with something queryable is a natural next step once one exists for the rest of the codebase.

## 6. Logging

**Finding**: ~44 `console.log/error/warn` calls total across `src/app/api` (5) and `src/lib` (39), all ad hoc unstructured strings with inconsistent bracket-tag prefixes (`[lead-extractor]`, `[signup]`, `[queue]`, etc.). No `src/lib/logger.ts` or equivalent exists. The only structured (JSON-shaped) logging anywhere is `src/lib/security/audit.ts`'s `audit()` calls for security/audit-trail events — a different purpose (persisted audit trail, not operational logging).

**What shipped this phase**: the new `withProtection` catch block's `console.error('[api] unhandled error:', err)` follows the existing bracket-tag convention rather than inventing a new one, since no shared logger exists yet to route it through.

**Deferred**: introducing a real structured/leveled logger (even a thin wrapper around `console` that emits JSON with a timestamp/level/module) is appropriately its own small, focused piece of work — not bundled into this phase, which already touches error handling, transactions, and the CRUD factory. Recommended as the next Phase 08-adjacent follow-up.

## 7. Caching

**Finding**: nothing exists. No `Cache-Control` headers, no `unstable_cache`/`revalidate`, no server-side response cache (in-memory or Redis) anywhere in the API layer. Every request recomputes/refetches from scratch beyond React Query's client-side `staleTime`.

**Not addressed this phase**: no route in the audit was found to be a clear, safe caching candidate without a product decision on staleness tolerance (most read endpoints are tenant-scoped and mutate frequently; the few public/anonymous endpoints like `public/blog` are low-traffic enough that caching isn't yet a measured problem). Documented as a deferred, low-priority item pending an actual performance signal.

## 8. Pagination, Filtering, Sorting

**Finding**: pagination was totally absent everywhere — the CRUD factory hardcoded `take: maxItems` (default 200) with no `skip`/cursor support, and no route (factory or bespoke) read a `?page=`/`?cursor=`/`?offset=` param; a `grep` for `skip:`/`cursor:` in `src/app/api` returned zero matches. This affects high-volume routes like `leads`, `notifications`, and audit logs directly. Filtering existed in 34 bespoke routes, each inventing its own query-param names/structure with no shared helper; all 91 CRUD-factory routes had zero filtering (list always scoped to `tenantId` only). Sorting was configurable in exactly one route (`leads/route.ts`, via `?sort=field:dir`); every other occurrence (73 of 74 `orderBy` usages, including all 91 factory routes) was a fixed `orderBy: { createdAt: 'desc' }`.

**What shipped this phase** — the CRUD factory (`src/lib/crud/domain-handler.ts`, backed by pure helpers in the new `src/lib/crud/query.ts`) now supports all three natively:
- **Pagination**: `?page=`/`?limit=` (capped at each domain's `maxListItems`, defaulting to it when unset — so every existing caller's behavior is unchanged unless it opts in). The list response now includes a `pagination: { page, limit, total, totalPages }` block alongside the existing `items` array (additive, doesn't break existing consumers that only read `.items`).
- **Filtering**: a new optional `DomainConfig.filterableFields: string[]` — when set, matching query params are applied as exact-match `where` conditions. Off by default (no config change required for existing 91 domains).
- **Sorting**: a new optional `DomainConfig.sortableFields: string[]`, following the same `?sort=field:dir` convention already established by `leads/route.ts`. `createdAt` is always sortable regardless of config. Falls back to `createdAt:desc` for a missing/invalid/disallowed field.

This is `adr/0003` territory extended: the factory gained real capability, but **no existing domain config was changed to opt into filtering/sorting** — that's a per-domain rollout decision (which fields make sense to filter/sort on varies by model) left as a documented, low-risk follow-up. The pagination change applies uniformly and safely to all 91 domains immediately since it degrades to the old behavior when unused.

**Deferred**: rolling `filterableFields`/`sortableFields` out to specific high-value domains (leads-adjacent, notifications, audit-log-shaped models); the ~34 bespoke routes' inconsistent filter param naming is a smaller, lower-urgency cleanup.

## 9. Business logic extraction — worked example

To demonstrate the "pull logic out of the controller, make it testable" pattern this phase's brief asked for (§2), `club/rewards/[id]/redeem/route.ts`'s redemption logic — including the concurrency-safe point-decrement fix from §4 — was extracted into `src/lib/club/redeem-reward.ts`. The route handler is now 12 lines: resolve `tenantId`, call `redeemReward(tenantId, id)`, return its result. This is also what made the race-condition fix independently integration-testable (see §10) without needing a full Next.js request/response mock.

This one extraction is a pattern to repeat, not a completed rollout — `payroll/run`, `progressive`, `agent/run`, and the other "heavy" offenders in §2 remain inline and are documented as deferred, prioritized by the ranking in §2.

## 10. Authorization

**Finding**: 4 RBAC helpers exist (`src/lib/auth/rbac.ts`): `hasPermission()` (5 files, 7 call sites, consistently used for granular team-management checks), `requirePermission()` (defined, **never called anywhere** — dead code), `isSuperAdmin()` (34 files, 47 call sites — the dominant default), and `isPlatformStaffAdmin()` (5 files). Usage is inconsistent, not absent: the `virtual-assistants` domain itself is split, with `virtual-assistants/route.ts` and `.../services` gating on `isPlatformStaffAdmin` while sibling routes `.../assignments` and `.../timesheets` gate on `isSuperAdmin` for what reads as the same class of internal-ops check. `isSuperAdmin` appears to have become the default fallback whenever *any* elevated check is needed, rather than staff-ops routes consistently reaching for the narrower, purpose-built `isPlatformStaffAdmin`. On the positive side: **zero** hand-rolled inline role checks were found anywhere in `src/app/api` (a `grep` for `user.role !==`/`.role === '...'` outside the 4 helpers turned up only data-shape usages, never authorization logic) — every actual authorization decision does route through one of the 4 helpers; the problem is *which* one, not bypassing them.

**Not addressed this phase**: reclassifying the ~15 `isSuperAdmin`-gated routes that look like they should use `isPlatformStaffAdmin` instead requires a per-route judgment call about intended scope (platform-global vs. internal-ops) that's a product/security decision, not a mechanical fix — documented as deferred, medium priority. `requirePermission()` being dead code is low-risk (an unused, harmless export) — left as-is rather than deleted, since removing an exported helper is exactly the kind of unrequested cleanup this project's discipline avoids doing opportunistically.

## 11. Background Jobs & Events

**Finding**: the job queue (`src/lib/queue/index.ts`) is a genuinely well-built abstraction — `QueueAdapter` interface, in-memory (dev) and Redis (prod, via `REDIS_URL`) implementations, a polling worker loop — but has exactly **one real call site** (`campaigns/[id]/send` → `enqueue('email_campaign', ...)`). Everything else that looks queueable runs synchronously in the request/response cycle, most notably `leads/search`, which does up to 20 sequential LLM calls (one per scraped lead, `await`ed in a loop) inside a single HTTP request — the sharpest timeout risk in the app. The queue's own `lead_enrich` job type exists specifically to make `leads/[id]/enrich` async but is dead code — nothing ever calls `enqueue('lead_enrich', ...)`; that route also runs its single LLM call synchronously. Several other "slow-looking" endpoints (`competitor-analysis/run`, `seo/[id]/crawl`, `analyzers/social/analyze`, `backlinks/discover`) are actually cheap because they return `Math.random()`-templated fake data rather than doing the real work their names promise — a separate correctness issue, noted in `KNOWN-ISSUES.md`-style follow-up, not a queuing gap. The queue has **no retry, no dead-letter handling, and no alerting**: a failed job is marked `failed` once with a truncated error string and never retried or surfaced proactively. There is **no cron/interval-based recurring work anywhere** in the backend — `setInterval` has zero matches in `src`, and "scheduler"-named modules (`campaign-scheduler`) are one-shot, on-demand LLM calls, not actual schedulers.

`emitNotificationEvent()` (confirmed a DB-persistence helper, not a pub/sub system — its own comment admits real-time push is an unimplemented placeholder) has 21 call sites across 10 files, using 10 different category strings, only 4 of which match the emitter's own documented taxonomy (`llm | onboarding | negotiation | system | billing | distributor` — actual usage never touches `system`, `billing`, or `distributor`). Usage is domain-inconsistent: `llm` and `negotiation` emit on nearly every state transition; comparably significant flows like `campaigns/[id]/send` and `leads/search` emit nothing.

**Not addressed this phase**: queuing `leads/search` and `leads/[id]/enrich` properly is real, valuable work, but changes the response contract (the client currently gets results synchronously; a queued version needs a polling or webhook completion path) — a UI-affecting change that needs its own scoped pass, not a drive-by backend fix. Retry/dead-letter/alerting on the queue worker, and reconciling the notification-category taxonomy, are both documented as deferred, medium-priority follow-ups.

## 12. API Versioning

**Finding**: confirmed total absence — no `/v1/`, `/v2/`, or `Accept-Version` handling anywhere in `src/app/api` or `src/proxy.ts`. Not addressed this phase; with zero external API consumers currently documented, introducing versioning now would be speculative. Recommended trigger: the first time a breaking route-shape change needs to ship without an in-lockstep frontend deploy (e.g., a public/partner API).
