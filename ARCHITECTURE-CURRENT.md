# ARCHITECTURE-CURRENT.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Describes the system **as it currently exists**, verified by direct code reading and three parallel deep-scan passes (backend/DB, frontend, security) — not the intended/originally-designed architecture (that's `TECHNICAL_SPECIFICATION.md`, which this document supersedes where the two differ).

## 1. Frontend architecture

**Routing model**: The authenticated app is architecturally a single-page app riding on Next.js. `src/app/page.tsx` holds a `useState<View>` and a `RenderView` switch with 62 `case` branches, each rendering one of 62 components from `src/components/dashboard/*.tsx`. Navigation is driven by `src/components/dashboard/sidebar.tsx`, whose `View` union type and nav-item config both independently list the same 62 ids — verified exact 1:1:1:1 match across switch/type/nav/component-file, **no orphaned or dangling views**. Only two real Next.js routes exist: `/` (the SPA shell) and `/invite/[token]` (added during this session's earlier phase). No other page has its own URL — deep-linking to a specific dashboard view is not possible.

**State management**:
- `useAppStore` (zustand, persisted to `localStorage` as `marketing-saas-store`): `activeTenantId`, `sidebarOpen`, and their setters. The only global tenant-context state on the client.
- `useAuthStore` (zustand, persisted as `marketing-saas-auth`): purely UI state for the login/signup modal (`authModalOpen`, `authModalMode`). Real session data lives in React context via `useAuth()` (`src/components/auth/session-provider.tsx`), fetched from `/api/auth/me`.

**i18n**: Custom context provider (`src/i18n/provider.tsx`), not the `next-intl` package that's listed as a dependency. 29 locale JSON files statically imported into a `DICTIONARIES` map; locale persisted via a 1-year `document.cookie`; `t()` falls back to the English dictionary on a missing key, and to the raw key string if even English is missing (visible as an intentional debug signal). RTL applied via `document.documentElement.dir`, driven by 3 of 29 configured locales (ar/he/fa). Deliberately cookie-based rather than URL-based, to preserve the single-route app shell.

**Data fetching**: TanStack Query v5 throughout. **No shared data-access hook exists** — 55 of 62 view components hand-roll their own `useMutation` + `fetch()` + `sonner` toast + `queryClient.invalidateQueries()` chain independently. 29 of 62 similarly hand-roll a create/edit dialog + local `useState` form-object pattern. This is the single largest missing-abstraction opportunity in the frontend (see DEAD-CODE.md for the related duplicate-toast-system finding).

**Component kit**: shadcn/ui (Radix UI primitives) under `src/components/ui/`, ~50 files. Several of these are mounted in the app but have zero real consumers beyond their own wrapper (dead — see DEAD-CODE.md).

## 2. Backend architecture

**Route handler patterns**: Two coexisting styles across 239 `route.ts` files in 76 domains:
1. **Generic CRUD factory** (`src/lib/crud/domain-handler.ts`, `createDomainHandlers`/`createDomainItemHandlers`) — used by 91 route files across ~46 domains (leads-adjacent CRM domains, content, SEO, social, ads, attribution, chatbot, workflows, webhooks, funnels, journeys, approvals, etc.). List/create scope by `requireTenantId()`; single-item update/delete additionally do a fetch-then-compare tenant-ownership check before mutating.
2. **Bespoke handlers** — everything else, with authorization falling into one of: `isSuperAdmin()`-gated (platform admin, internal HR, platform finance/promotions, distributors), `getCurrentUser()`-gated (LLM console, negotiation, virtual assistants, support plans, payroll, graph orchestrator, onboarding sessions), `requireTenantId()`-only (leads, campaigns, projects, billing, most CRM/marketing bespoke routes), or intentionally public (auth login/signup, health check, `/api/public/*`, promo-link click tracking, team-invite acceptance, sandbox demo start).

**The tenant-context resolver is the architectural root of most authorization gaps** — see SECURITY-BASELINE.md §Authorization for the full writeup. In short: `requireTenantId()` (`src/lib/tenant.ts`) resolves tenant scope from (1) the authenticated session, falling back to (2) an `X-Tenant-ID` request header or (3) a `tenant-id` cookie — neither of which requires the caller to actually be that tenant's user. The generic CRUD factory's list/create operations rely on this resolver alone, with no additional per-user permission check.

**AI/LLM layer — two disconnected stacks**:
- `src/lib/llm/aggregator.ts` — the documented, "real" system: 5 free-tier providers (Groq, Cerebras, OpenRouter, Mistral, HuggingFace) each with a strategy-pattern adapter making real HTTP calls, automatic fallback on rate-limit/error, per-provider cooldown, and DB-persisted daily/monthly quota tracking (`LlmProviderConfig`, `LlmUsageRecord`, `LlmAuditEvent`).
- `z-ai-web-dev-sdk` — used directly (bypassing the aggregator entirely) by lead enrichment, `/api/ai/generate`, `/api/diagnostics/run`, `/api/reports/monthly/generate`, and `/api/leads/search`. No environment variable anywhere configures it; a code comment in `src/lib/ai/lead-extractor.ts` states it's "already wired up" in "this Next.js sandbox" — i.e. it appears to depend on an implicit runtime from the platform this project was originally built on, not something a self-hosted deployment can configure. Every call site wraps it in try/catch with a rule-based fallback, so failures degrade rather than crash, but this means a chunk of the app's AI features (lead enrichment quality, diagnostics, monthly report generation) silently run on fallback logic rather than an LLM in any deployment outside that original sandbox.

By contrast, the LLM aggregator, vector search, and email service are all consistently guarded with try/catch + graceful fallback.

## 3. Database architecture

- 150 Prisma models, SQLite for dev (`DATABASE_URL=file:./db/custom.db`), PostgreSQL documented for production but not independently verified running in this audit.
- **No `prisma/migrations/` directory exists.** The project uses a schema-push workflow (`prisma db push`) for dev. The production deploy script (`scripts/deploy.sh`) runs `prisma migrate deploy`, which has no migration history to apply against a fresh database — a real deploy-path defect (the VPS deploy script, `deploy-vps.sh`, hedges with a `db push` fallback; `deploy.sh` does not).
- Models group into ~28 logical domains (auth/tenant/RBAC, CRM, email, SEO, content, social, ads, analytics/attribution, AI agents, competitor intel, conversational/reputation, growth tooling, billing, social listening, pricing/unlock, public/marketplace, customer club, e-commerce, reseller/distribution, payments, investor matching, internal HR/finance, AI/LLM infra, onboarding/negotiation, VA/support services, vector search, white-label, messaging) — full model-to-group mapping available in the backend discovery agent's transcript if needed for reference; not reproduced in full here to keep this document scannable.
- 52 of 150 models have no `tenantId` field — the large majority of these are legitimate platform-global config/reference tables (`Tenant` itself, `Permission`, pricing/license tables, internal HR, LLM provider config) or child-of-child models scoped transitively through a parent foreign key (e.g. `SeoPage` via `seoProjectId`). Not a defect as a category, but worth re-auditing individually before assuming every one is intentional.
- Of 89 direct `Tenant` relations: 77 use `onDelete: Cascade`, 9 use `onDelete: SetNull`, 3 have no explicit action (defaults to restrict) — deleting a `Tenant` row cascades through the large majority of that tenant's data by design.

## 4. Security architecture (summary — full detail in SECURITY-BASELINE.md)

- Custom HMAC-SHA256 session cookie, `httpOnly`, `secure` in production, 30-day expiry (browser-side only — server-side tokens never expire and cannot be individually revoked; only rotating the global secret invalidates everyone at once).
- `src/proxy.ts` is the single global auth gate: it 401s any request to a non-public route/page without a validly-HMAC-signed session cookie, adds security headers (CSP, HSTS in prod, X-Frame-Options, etc.), rejects path-traversal/control-character paths, and applies an Origin-header CSRF check on state-changing methods.
- Because self-signup is open and public (`POST /api/auth/signup`), the practical bar to becoming "an authenticated attacker" against this system is simply signing up for a free account — several of the cross-tenant IDOR findings in SECURITY-BASELINE.md require only that, not a privileged or anonymous position.
- A formal Role/Permission RBAC system exists in the schema (`Role`, `Permission`, `RolePermission`) but is currently unreachable: `getCurrentUser()` never returns the `roleId` field that `src/lib/auth/rbac.ts`'s permission checks read, and `hasPermission()`/`requirePermission()` are not called from any live API route — actual authorization in the codebase is almost entirely ad hoc `isSuperAdmin()` / `user.role === 'x'` / tenant-id-comparison checks per route, not the formal system.

## 5. Deployment architecture

Docker Compose (separate dev/prod files) with the app, PostgreSQL, and Redis as services; Caddy in front for automatic HTTPS. Two deploy paths are scripted (`scripts/deploy.sh` for an already-provisioned server, `scripts/deploy-vps.sh` for a fresh VPS including Docker install + rsync + Caddy config). No CI/CD pipeline triggers any of this automatically — deployment is a manually-run script.
