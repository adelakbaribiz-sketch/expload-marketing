# ARCHITECTURE-TARGET.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04, Phase 3 (Architecture Recovery). Summarizes the target architecture and every proposed change as Current → Problem → Target → Migration Strategy. Full detail for each item lives in its own ADR under `adr/`; this document is the index and the executive summary. See also `SYSTEM-DIAGRAM.md`, `MODULE-BOUNDARIES.md`, `DEPENDENCY-RULES.md`.

## Topology decision: Modular Monolith (confirmed, not changing)

**Decision** (full reasoning in `adr/0001-modular-monolith-over-microservices.md`): this codebase stays a single Next.js deployable. No microservice extraction. The dependency-graph audit found the internal module structure is *already* a clean, low-coupling DAG with zero circular dependencies — the boundaries a microservice split would try to create largely already exist as `src/lib/` modules. Splitting them into separate deployables today would add real operational cost (network calls, distributed transactions, separate CI/CD/observability) while removing very little actual coupling, since there isn't much coupling to remove. The one place genuine service-like coupling exists — the graph orchestrator's internal HTTP self-calls — is a pattern to *fix within* the monolith (ADR-0005), not evidence those domains want to be separate services.

**Revisit condition**: only if a specific domain (most plausibly the LLM/AI layer or the job queue, given their external-dependency/latency profile) develops a real, evidenced need to scale or fail independently under production load — not speculatively.

### Database-change safety procedure (applies specifically to item 6, and to any future schema change)

Per this migration's Step 10 requirement — no database refactor proceeds without all four of these defined first:

1. **Backup**: a full database dump (`pg_dump` for Postgres prod, or a copy of the SQLite file for dev) taken immediately before any migration is generated or applied — never assume the last backup is recent enough.
2. **Migration**: generate via `prisma migrate dev --name <descriptive-name>` in development first, never hand-write SQL against production directly; review the generated SQL diff before it touches any real data, especially watching for any `DROP COLUMN`/`DROP TABLE` Prisma infers from a schema change that was meant to be additive.
3. **Validation**: apply the migration to a copy of production data (or a realistic staging dataset) first; confirm row counts and a sample of critical records (users, tenants, payments) are unchanged where they shouldn't have changed, and that the application boots and serves the smoke-tested critical paths (login, dashboard load, one CRUD operation per major domain) against the migrated schema.
4. **Rollback**: for the baseline migration specifically (ADR-0006 step 1-2), rollback is "the backup taken in step 1, restored" — Prisma migrations don't have a generic auto-down migration, so every future migration's rollback plan must be written by hand at the time it's created, not assumed to exist generically. No schema change ships without its own explicit, written rollback step from this point forward.

## What this document deliberately does NOT propose

- **No microservice extraction** (ADR-0001).
- **No rewrite of the CRUD factory pattern** — it's confirmed genuinely well-built; extend it (ADR-0003), don't replace it.
- **No change to the modular-monolith's module layout** (`src/lib/` by domain) — it's already sound; the fixes above are about closing specific gaps, not restructuring what's already a clean DAG.
- **No new abstraction layer between routes and the database for the ~30 bespoke, non-factory routes that are already correctly delegating to a `src/lib/` service** (negotiation, payroll's *intent* even if not yet its implementation, payments) — that pattern is correct, just inconsistently applied; the fix is applying it more consistently (item #4 in `MODULE-BOUNDARIES.md`'s violations list — payroll, billing/calculate, and club/membership should get the same treatment negotiation already has), not inventing a new pattern.

## Sequencing recommendation

If working through this list, this order minimizes risk and maximizes early value: **#3 (tenant-context) and #7-step-1 (session expiry) first** — both small, both close real security gaps, both from `KNOWN-ISSUES.md`'s highest-severity items. Then **#6 (migrations)** before any further schema changes are made in later phases of this project, so subsequent work doesn't add to the `db push` risk. Then **#2 (CRUD factory hooks)** since several other planned fixes (Funnel/Journey validation, distributor payouts) depend on having somewhere to put the rule. **#1/#8 (AI consolidation)** and **#4/#5 (autonomous agent)** are larger, more deliberate efforts — schedule as dedicated work, not squeezed alongside feature development, given the lack of automated tests to catch a regression.
