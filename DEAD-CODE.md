# DEAD-CODE.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04. Everything below is code that exists in the repo, is reachable/importable, but has zero live consumers or is otherwise unreachable in normal operation — confirmed via import/reference grep, not assumption. Nothing in this document has been deleted; this is an inventory for a future, deliberate cleanup pass.

## 2. Dead shadcn/ui wrapper components

These files exist under `src/components/ui/` and are syntactically fine, but nothing in the app ever renders them:

- `src/components/ui/carousel.tsx` — only consumer of `embla-carousel-react`; zero renders elsewhere.
- `src/components/ui/input-otp.tsx` — only consumer of `input-otp`; zero renders elsewhere.
- `src/components/ui/drawer.tsx` — only consumer of `vaul`; zero renders elsewhere.
- `src/components/ui/chart.tsx` — a `recharts` wrapper; zero renders elsewhere (the app's actual chart usage in `analytics-view.tsx` etc. imports `recharts` directly, not through this wrapper).
- `src/components/ui/sidebar.tsx` — the generic shadcn sidebar primitive, entirely distinct from the real, hand-built `src/components/dashboard/sidebar.tsx` that the app actually uses. Zero consumers.

**Note**: removing these components should happen *together with* removing their corresponding now-unused npm packages (§1/DEPENDENCY-AUDIT.md §3) in one cleanup commit, verified with a full typecheck+build afterward.

## 3. Duplicate, partially-dead toast system

`src/app/layout.tsx` mounts **two** toast providers simultaneously: `<Toaster>` from `@/components/ui/toaster` (shadcn's Radix-based toast system, driven by `useToast()` in `src/hooks/use-toast.ts`) and `<Toaster>` (aliased `Sonner`) from `@/components/ui/sonner`. In practice:
- `src/hooks/use-toast.ts` has exactly **one** consumer: `src/components/ui/toaster.tsx` itself.
- All 57 live toast call sites across the 62 dashboard views use `sonner`'s `toast.*()` directly.

The shadcn toast stack (`ui/toaster.tsx` + `hooks/use-toast.ts`) is mounted in the app shell on every page load, consuming a render slot and bundle size, but is never actually triggered by any feature code. **Recommendation**: remove `<Toaster>` (shadcn) from `layout.tsx`, and delete `ui/toaster.tsx` + `hooks/use-toast.ts` + the underlying `ui/toast.tsx` primitive, keeping only the sonner path that's actually used.

## 4. Dead authorization subsystem

The formal Role/Permission RBAC system (`Role`, `Permission`, `RolePermission` Prisma models, plus `hasPermission()`/`requirePermission()`/`getUserPermissions()` in `src/lib/auth/rbac.ts`) is unreachable in current wiring:
- `getCurrentUser()` (`src/lib/auth/simple-session.ts`) never returns a `roleId` field.
- `rbac.ts`'s permission functions read `(user as any).roleId`, which is therefore always `undefined`, so their DB-backed permission-lookup branch never executes.
- `hasPermission()`/`requirePermission()` are not called from any live API route (confirmed via repo-wide grep — only self-referenced within `rbac.ts`).

This is architecturally significant, not just an unused helper: real authorization in this codebase is done via ad hoc `isSuperAdmin()` / `user.role === 'x'` string checks and tenant-id comparisons scattered per-route, not this formal system, even though the formal system's schema and UI (the custom-role editor added earlier this session in `team-view.tsx`) exist and are reachable — a customer can create a custom role with a specific permission set through the UI, and it will have **zero actual effect** on what that user can do, because nothing in the request path ever checks it. **Recommendation**: this needs a decision, not a quiet deletion — either wire `roleId` through `getCurrentUser()` and start enforcing it (real feature completion), or remove the custom-role-editing UI and be explicit that role granularity isn't supported yet (honest scope reduction). Leaving it as-is is the worst option: it presents working functionality that silently does nothing.

## 5. Vestigial database model

`Cohort` (`prisma/schema.prisma`) — has no API route anywhere under `src/app/api`, and no code anywhere in `src/` references the `cohort` Prisma client accessor. Confirmed already in an earlier phase of work on this project and re-confirmed by this audit's backend scan. Not wired to anything; a genuinely vestigial table. **Recommendation**: needs a product decision on its intended purpose before either building an API/UI for it or removing it from the schema — do not guess at what "cohort" was meant to track here.
