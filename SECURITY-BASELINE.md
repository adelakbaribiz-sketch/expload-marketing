# SECURITY-BASELINE.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04, via a dedicated security-focused deep-scan pass plus independent verification of the highest-severity claims against actual code (`src/proxy.ts`, `src/lib/tenant.ts`) before publishing this document. Severity levels reflect **real reachability given `proxy.ts`'s actual auth gate** — see the calibration note below before reading the findings, since it materially changes several severities from a naive reading of the code in isolation.

## Calibration note — read this first

`src/proxy.ts` requires a validly-HMAC-signed session cookie for every route/page **except** this exact allowlist: `/api/health`, `/api/auth/{login,signup,logout}`, `/api/public/*`, `/api/webhooks/*`, `/api/seed`, `/api/team/invite/*`, `/api/sandbox/{start,action,convert}`, plus a handful of public marketing pages. Everything else 401s at the proxy layer before ever reaching a route handler. This means:
- Findings below marked **[Anonymous-reachable]** require zero account and are the most urgent.
- Findings marked **[Authenticated-reachable]** require *some* valid session — but since `POST /api/auth/signup` is itself public and unrestricted, this is a trivially low bar (sign up for a free account, then attack), not a meaningfully protective barrier. Treat these as real, not theoretical.

## 1. Authentication / Session

- **[Medium] Session tokens never expire server-side and cannot be individually revoked.** `src/lib/auth/simple-session.ts:31-48` — the signed token is `userId.HMAC(userId)`, no timestamp/nonce claim. `verifySessionToken` checks signature validity only. The 30-day cookie `maxAge` (line 58) is a client-side hint only; a leaked/copied token remains valid indefinitely if replayed, and logout (`clearSessionCookie`) only removes the client cookie — it doesn't invalidate the token server-side. The only way to invalidate all sessions at once is rotating `NEXTAUTH_SECRET`, which logs out every user simultaneously. *Fix*: add an expiry claim to the signed payload and check it on verify; consider a minimal revocation mechanism for logout/incident response.
- **[Low] `proxy.ts` validates signature format only, not live account state.** `src/proxy.ts:34-46` (`isValidSessionFormat`) doesn't check that the referenced user still exists or is active — that only happens later, in `getCurrentUser()` (`simple-session.ts`), which does correctly check `user.isActive` and `user.tenant.isActive` and returns `null` if either is false. The practical consequence is finding #3 in §2 below (tenant-context header fallback), not a standalone issue.
- **[Info] Password hashing is bcryptjs, cost factor 12** (`src/lib/auth/password.ts:12`) — reasonable, standard.
- **[Confirmed, latent — not currently exploited] RBAC granular Role/Permission system is dead code.** `src/lib/auth/rbac.ts:40,84` read `(user as any).roleId`, which `getCurrentUser()` never populates — always `undefined`. `hasPermission()`/`requirePermission()` are not called from any live API route (confirmed via repo-wide grep), so this has no current blast radius, but see `DEAD-CODE.md` §4 — the custom-role-editor UI built on top of this schema presents functionality that silently does nothing.

## 2. Authorization / Tenant Isolation

- **[Critical][Authenticated-reachable] Support-plan tickets and subscriptions have zero tenant-ownership check.** `src/app/api/support-plans/tickets/route.ts` PATCH (lines 67-91) and `src/app/api/support-plans/subscriptions/route.ts` PATCH (lines 64-73) both do `db.<model>.update({ where: { id: body.id }, data })` with no `tenantId` filter. Any signed-up user, of any tenant, can read (via the echoed response), reassign, resolve, message on, or cancel any other tenant's support ticket or paid subscription by guessing/enumerating an id. *Fix*: add `tenantId` to the `where` clause, matching the ownership-check pattern already correct elsewhere (e.g. `src/lib/crud/domain-handler.ts`'s `requireOwnedItem`, or `src/app/api/reseller/applications/[id]/route.ts`).
- **[High][Authenticated-reachable] `GET /api/tenants` has no auth check and discloses every tenant's id/name/domain/plan/record-counts.** `src/app/api/tenants/route.ts:13-19`. `POST /api/tenants` is rate-limited only, not authenticated — any signed-up user can enumerate every tenant in the system (making finding #3 below far easier to exploit) and create arbitrary new tenants. *Fix*: scope GET to the caller's own tenant or gate to superadmin; require an authenticated context for POST.
- **[High][Authenticated-reachable] `requireTenantId()` falls back to a client-supplied `X-Tenant-ID` header or `tenant-id` cookie whenever the session-derived tenant is null.** `src/lib/tenant.ts:12-24`. Verified directly: priority order is (1) session-derived tenant, (2) `X-Tenant-ID` header, (3) `tenant-id` cookie — the header/cookie is **only** consulted when step 1 returns null, which (given `proxy.ts` already blocks requests with no/invalid-format cookie) means this is reachable specifically by a caller holding a validly-signed session cookie for a user or tenant that has since been deactivated/deleted. This affects every one of the ~46 domains built on the generic CRUD factory (`src/lib/crud/domain-handler.ts`), whose list/create path relies on `requireTenantId()` alone with no further check. *Fix*: don't fall back to client-supplied headers/cookies on routes that expect an authenticated session — either 401 when `getAuthTenantId()` is null, or restrict the header/cookie fallback to routes explicitly designed for external API-key-style access.
- **[High][Authenticated-reachable] `PATCH`/`DELETE /api/marketplace/products/[id]` have no auth check and mass-assign the raw request body.** `src/app/api/marketplace/products/[id]/route.ts:11-22` — `db.apiProduct.update({ where: { id }, data: body })`. Any signed-up user can modify or delete any other tenant's marketplace listing.
- **[High][Authenticated-reachable] `POST /api/leads/[id]/enrich` and `POST /api/campaigns/[id]/send` have no ownership check on the id.** Cross-tenant AI-enrichment trigger and cross-tenant email-campaign send trigger by id guessing.
- **[High][Anonymous-reachable] `GET /api/queue` has no auth and lists background jobs across all tenants**, unfiltered — though this route is not in `proxy.ts`'s public allowlist, so in practice it also requires a signed-up account, same as the findings above; noting separately since it leaks cross-tenant job metadata (e.g. `campaignId`s) rather than a specific resource.
- **[Pass — verified correct, sampled]**: `src/lib/crud/domain-handler.ts` (list/create scope by `requireTenantId()`, single-item update/delete additionally fetch-then-compare ownership); `src/app/api/distributors/route.ts` + `[id]/route.ts`; `src/app/api/reseller/opportunities/[id]/apply/route.ts`; `src/app/api/reseller/applications/[id]/route.ts`; `src/app/api/distributors/payouts/route.ts` (superadmin-gated approve/pay actions, correctly).

## 3. Input Validation

- **[Medium] Only 9 of 239 route files (~3.8%) use zod schema validation** — `tenants`, `templates`, `team/invite` (+`[token]`), `projects`, `leads`, `campaigns`, `auth/signup`, `auth/login`. The rest read `req.json()` directly, with manual `Number()`/`String()` coercion and `sanitizeText()`-family stripping (HTML tags, length clamps) applied inconsistently.
- **[Medium] The generic CRUD factory has no type/format/enum validation**, only a field-name allowlist (`src/lib/crud/domain-handler.ts:43-55,86-101`). No SQLi risk (Prisma parameterizes) and XSS is mitigated by `sanitizeText`, but no data-integrity guarantee across the ~46 domains that use it.
- **[Medium] Several unvalidated bespoke routes write raw body fields with no sanitization at all** (unlike `leads/route.ts`, which does sanitize): `distributors/route.ts` POST (no length/format limits on contact fields), `distributors/payouts/route.ts` POST (`db.distributorPayout.create({ data: body })` — literal mass-assignment, though superadmin-gated), `support-plans/{subscriptions,tickets}/route.ts` POST, `onboarding/route.ts` POST.

## 4. Secrets Scan

- **[Critical][Anonymous-reachable] `POST /api/seed` — public, unrated-limited, discloses plaintext credentials for a real persisted account.** `src/app/api/seed/route.ts:22-41` sets password `demo12345` on `admin@expload.io` (creating it as `role: 'owner'` if absent) and **unconditionally returns those plaintext credentials in the JSON response** (lines 118-121), regardless of branch taken. Listed in `proxy.ts`'s `PUBLIC_API_ROUTES` — confirmed genuinely reachable with zero authentication, zero rate limit, repeatably, in any environment (no `NODE_ENV` gate) including the documented Docker/Caddy production deploy path. This is the single highest-priority fix in the entire audit.
- **[Info] No hardcoded real-looking API keys/secrets found** anywhere in `src/`/`scripts/` beyond the documented, fail-closed-in-production dev fallback secret in `simple-session.ts:23`.
- **[Info] `.env` hygiene confirmed clean** — gitignored, never committed (`git log --all --full-history -- .env` returns nothing).

## 5. CSRF / CORS / Headers

- **[Medium] Production CSP allows `script-src 'self' 'unsafe-inline'`** (`proxy.ts:94-96`, duplicated independently in `src/lib/security/headers.ts:21-25` — these two files must be kept in sync by hand, a maintenance-drift risk in itself). Materially weakens CSP as an XSS backstop; rest of the policy is otherwise tight (`object-src 'none'`, `frame-ancestors 'none'`, scoped `connect-src`).
- **[Pass] CSRF Origin-check confirmed correct** (`proxy.ts:172-187`) — rejects state-changing requests when a present `Origin` header doesn't match the app's own origin; absent-`Origin` requests pass through by documented design (non-browser clients).
- **[Pass] No CORS misconfiguration found** anywhere in `src/app/api` — no wildcard or permissive `Access-Control-Allow-Origin`.
- **[Pass] Webhook signature verification confirmed real** — `src/app/api/webhooks/crypto/nowpayments/route.ts` verifies HMAC-SHA512 via `timingSafeEqual` before acting on any payload.

## 6. Rate Limiting

- **Coverage: `withProtection` (the only mechanism applying rate limits) is used in 79 of 239 route files (~33%).** Auth endpoints are correctly covered (`rateLimit: 'auth'` on login/signup).
- **[High] `/api/seed` has zero rate limiting**, compounding finding #4 above.
- **[Medium] The three public `/api/sandbox/*` routes have zero rate limiting** and write a new `Tenant`+`SandboxSession` row per call.
- **[Low] Mixed coverage within single files is common** — e.g. `leads/route.ts` POST is wrapped, GET is not; the CRUD factory wraps POST/PATCH/DELETE but not either GET path.
- **[Info] Rate limiter is in-memory/single-process by design** (documented in code comments) — matches the current single-container deployment; would need a Redis-backed store (Redis is already provisioned for the job queue) before any horizontal scaling.
- **[Low] `X-Forwarded-For` is trusted unconditionally by `getClientId()`** — correct today only because the documented `Caddyfile` overwrites (not appends) that header before it reaches the app; would become spoofable behind a different reverse proxy, or if the app is ever exposed directly (the prod compose does publish port 3000 to the host).

## 7. Dependency Notes

- No `eval()`, `new Function()`, or `child_process` usage anywhere in `src/`/`scripts/`.
- `bcryptjs` / `ioredis` usage both reasonable — see `DEPENDENCY-AUDIT.md` §4 for detail.
- **[Info] No password-reset API route exists** despite `/forgot-password`/`/reset-password` being public *pages* per `proxy.ts` — not itself a vulnerability (no endpoint to attack), but confirms those pages have no working backend today.
