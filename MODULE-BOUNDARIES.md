# MODULE-BOUNDARIES.md — Expload Marketing SaaS

Generated by discovery audit, 2026-09-04, Phase 3 (Architecture Recovery). Defines the layers this codebase should respect, states what each layer's job is (and isn't), and lists confirmed current violations. This document is prescriptive going forward — `DEPENDENCY-RULES.md` is the enforceable version of the same boundaries.

## The four layers

```
┌─────────────────────────────────────────────────────────┐
│ 1. UI layer — src/components/**, src/app/(pages)         │
│    Job: render, collect input, call fetch(), show state. │
│    Must NOT: contain business rules, call Prisma/db,     │
│    import anything server-only (auth internals, node:*). │
├─────────────────────────────────────────────────────────┤
│ 2. HTTP layer — src/app/api/**/route.ts, src/proxy.ts    │
│    Job: parse request, authenticate/authorize, validate  │
│    input, call into layer 3, shape the HTTP response.    │
│    Must NOT: contain multi-step business logic,          │
│    calculation formulas, or state-machine transitions —  │
│    those belong in layer 3 so they're testable and       │
│    reusable outside an HTTP context.                     │
├─────────────────────────────────────────────────────────┤
│ 3. Service/domain layer — src/lib/**                     │
│    Job: business logic, calculations, state machines,    │
│    external API integration (with fallback), validation  │
│    rules. Must be callable without a NextRequest.         │
│    Must NOT: import next/server, NextRequest/Response,    │
│    or anything that only exists inside a route handler.  │
├─────────────────────────────────────────────────────────┤
│ 4. Data layer — Prisma client (src/lib/db.ts), schema     │
│    Job: persistence, tenant-scoping enforcement via the   │
│    query shape itself where practical.                   │
└─────────────────────────────────────────────────────────┘
```

**Allowed dependency direction**: 1 → 2 → 3 → 4, and 1 → 2 directly (a UI component calling an API route via `fetch` is the *only* sanctioned way layer 1 talks to anything below it). No layer may depend on a layer above it. `src/proxy.ts` is a documented, intentional exception to the layer-2-imports-layer-3 rule (it inlines its own auth logic because it runs on the Edge runtime, which can't reliably import the shared `src/lib/auth` module) — this is the **only** sanctioned boundary exception in the codebase; any other cross-boundary shortcut found is a real violation, not precedent.

## What each layer currently looks like in this codebase (recovered)

- **Layer 1 (UI)**: 62 dashboard view components + ~50 shadcn primitives + the SPA shell (`page.tsx`). **Confirmed exhaustively clean**: only 3 `src/components → src/lib` imports exist repo-wide, and all 3 are safe (two are the pure `cn()` utility; one, `guided-tour.tsx` → `guides/section-guides.ts`, reaches into `src/lib` directly instead of via `fetch()`, but that lib file is confirmed pure static data with no server-only code — a stylistic inconsistency, not a real violation). Zero components import `@/lib/db` or any auth-internals module.
- **Layer 2 (HTTP)**: 239 route.ts files. Two sub-styles: (a) the generic CRUD factory (~46 domains) collapses layers 2+3+4 into one generic function with no domain-specific service layer at all — confirmed genuinely generic (no `if (model === X)` special-casing found anywhere in its 118 lines); (b) bespoke routes, which inconsistently either delegate to a `src/lib/` service (negotiation — cleanly, all 4 negotiation routes are thin) or embed substantial business logic directly in the handler (confirmed in at least 4 routes — see Violation 4 below).
- **Layer 3 (Service)**: ~41 modules under `src/lib/`. **Confirmed a clean DAG — zero circular dependencies found**, traced 3-5 hops deep across every module. 17 service modules are correctly marked `'server-only'` and none of them import `next/server`/`NextRequest`/`NextResponse` — the HTTP/service separation is real and consistently upheld everywhere except the CRUD factory (which deliberately mixes them, since its entire job is to *produce* route handlers). No true "god module" exists; the largest file (`negotiation/engine.ts`, 706 lines) is a clean Strategy/State-pattern implementation, not a dumping ground.
- **Layer 4 (Data)**: single Prisma client (`src/lib/db.ts`, fan-in 17 lib modules + 133 routes — an expected hub, not a violation), 150 models, no migration history (see `KNOWN-ISSUES.md` #16).

## Confirmed current boundary violations

1. **Tenant-context resolution (layer 3 → layer 2 concern leak)**: `src/lib/tenant.ts`'s `getTenantId()` treats an HTTP-layer concept (a request header) as equally trustworthy as a service-layer concept (the authenticated session) — the direct cause of the multi-tenancy findings in `SECURITY-BASELINE.md`. See ADR-0004.
2. **The CRUD factory has no service layer for domains that need real business rules** — true today for Funnel/Journey (no validation) and the distributor-payout domain (unvalidated, uncalculated amounts, per `BUSINESS-RULES.md` §5). See ADR-0003.
3. **Two AI integration stacks with no shared boundary**: `z-ai-web-dev-sdk` is called directly from exactly 5 call sites (`ai/lead-extractor.ts`, `api/ai/generate`, `api/diagnostics/run`, `api/reports/monthly/generate`, `api/leads/search` — confirmed centralized to just these 5, not scattered further) rather than through a shared service the way `llm/aggregator.ts` correctly centralizes its 5 real providers. See ADR-0002.
4. **Business logic embedded directly in route handlers, with no `src/lib/` module at all**, in at least 4 places: `api/payroll/run/route.ts` (full revenue-split formula inline, no `src/lib/payroll/` module exists), `api/billing/calculate/route.ts` (full pricing-calculator + ROI-estimation logic inline), `api/club/membership/route.ts` (tier-upgrade eligibility logic evaluated **and written to the DB inside a `GET` handler** — a smell independent of the extraction issue; default tier/reward seed data also hardcoded inline rather than in a seed/lib module), and `api/agent/run/route.ts` (a full second, independent 250-line "autonomous agent" implementation using static rules — see Violation 5).
5. **Duplicate, non-communicating "autonomous agent" concepts**: `src/lib/graph/orchestrator.ts` is documented in its own comment as "the brain that connects all platform modules into one autonomous system" (LLM-driven DAG planner). `api/agent/run/route.ts` independently reimplements a parallel notion of "autonomous marketing agent" — 9 hardcoded phases of stat-gathering and rule-based task creation, no LLM, no `src/lib/` module, and it never references `graph/orchestrator.ts` or vice versa. Two competing implementations of the same product concept exist side by side. See ADR-0005.
6. **A centralized prompt catalog that's mostly bypassed**: `src/lib/prompts/system-prompts.ts` defines 17 named prompts; a repo-wide search for `getPrompt(` found only 2 live call sites (both in `graph/orchestrator.ts`). The 6 dedicated negotiation prompts and the lead-enrichment prompt sit unused because `negotiation/engine.ts` and `ai/lead-extractor.ts` each define their own inline duplicate prompt instead of importing from the catalog built for exactly this purpose.
7. **Invisible runtime coupling via internal HTTP self-calls**: `src/lib/graph/orchestrator.ts`'s `NODE_EXECUTORS` reaches ~15 other API domains (leads, campaigns, competitor-analysis, content, social, SEO, ads, negotiation, onboarding, diagnostics, reports, virtual-assistants, payments) via runtime `fetch()` calls to its own server rather than direct module composition — a static import-graph analysis undercounts this module's true coupling entirely, and any of those 15 routes changing its request/response shape breaks the orchestrator with no compile-time signal.
8. **2 fully dead `src/lib/` modules, zero importers anywhere**: `src/lib/payment/gateway-router.ts` (192 lines — a complete, apparently-finished multi-gateway routing implementation that the actual `api/payments/gateways/route.ts` never calls; this is *separate* from and in addition to the "11 gateways are stubs" finding in `KNOWN-ISSUES.md` #7 — the router that would call them isn't even wired in) and `src/lib/onboarding/extractor.ts` (89 lines — PDF/DOCX text-extraction code that `api/onboarding/crawl/route.ts` never calls; **this refines `DEPENDENCY-AUDIT.md`'s earlier finding that `mammoth`/`pdf-parse` are "used"** — the npm packages are imported by this file, but the file itself is never invoked, so document upload/parsing in the onboarding wizard does not actually run today despite the packages being installed and the code existing).

**Positive findings worth preserving as new work continues** (not everything found was a problem): zero circular dependencies anywhere in `src/lib/`; all 5 real external-service integrations (LLM, vector, queue, email, crypto-payment) are confirmed single, uncircumvented entry points with no bypasses; the notification-event system (`emitNotificationEvent`) is a genuinely well-adopted cross-cutting pattern used from 10 call sites across 8+ unrelated domains, not a designed-but-abandoned abstraction.
